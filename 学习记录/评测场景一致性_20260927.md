# 评测场景一致性：考卷的问法和训练的问法不一样（2026-09-27）

本文件记录一次**评测协议层面**的发现与建议。起因是学生问「为什么换个问法分数差 26 个点」，
追下去发现问题比"措辞不同"更深一层。

沿用本项目纪律：**能核对的事实 / 解释（可能错）/ 未证实未测量** 三层分开。

> 「基准无 system message **且**措辞不同」。
> 我第一遍没搜到，是因为 grep 用了中文"系统提示"，而文档写的是英文 "system message"。

## 一、差异的精确条件（能核对的事实）

同一批 252 道冻结题、同一张图（`images` 字段逐条相同），**只差喂给模型的那段对话结构**：

| | 训练时 | 考卷上 |
|---|---|---|
| 系统提示词 | **有** | **完全没有这一段** |
| 消息条数 | 2（`system` + `user`） | **1（只有 `user`）** |

**代码出处**：

- 训练的数据格式：`code/projects/wafer-defect-vlm/src/wafer_vlm/curate.py:268-272`
  （`system` + `user` + `assistant` 三条消息）
- 训练用的系统提示词：`curate.py:35`
  `SYSTEM = "你是半导体晶圆 BIN 图缺陷分析专家，只依据图像回答，不推测工艺根因。"`
- 考卷的请求构造：`code/projects/wafer-defect-vlm/src/wafer_vlm/benchmark.py:187` 与 `:194`
  ```python
  "messages": [{"role": "user", "content": f"<image>\n{prompt}"}],
  ```
  **只有一条 user 消息，没有 system。**

**统计复核**（我逐条数过）：

| 文件 | role 组合 | 条数 |
|---|---|---|
| `benchmark/all_requests.jsonl` | `('user',)` | **1512 条，全部如此** |
| `results/reports/aux_trainfmt_requests.jsonl` | `('system', 'user')` | 252 条，全部如此 |

**而且项目自己的规范是要求带 system 的** —— `AGENTS.md` §5.6 的多模态对话示例里
第一条就是 `{"role":"system", ...}`。**所以考卷偏离了项目自己写的规范**，
`benchmark.py` 里也**没有注释解释为什么省掉**。

## 三、机制：不是"答得差"，是"答案塌缩"（本次新增，能核对的事实）

我把两批输出逐样本比对（`results/raw_outputs/qwen35_9b_adapter.jsonl` 与
`qwen35_9b_adapter_trainfmt.jsonl`，各 252 条）：

- 两种问法**答完全一样**的：**161 条**
- 两种问法**答不一样**的：**91 条**
- 两种问法下**无法解析成合法类名**的：**各 0 条** ← 所以**不是解析问题**

**预测分布对比**（"判成"= 模型给出的答案计数，不是真值）：

| 类别 | 考卷问法判成 | 训练问法判成 | 真值 |
|---|---|---|---|
| **Scratch** | **3** | **37** | 30 |
| **Donut** | **9** | **28** | 30 |
| **Loc** | **56** | 30 | 30 |
| Edge_Loc | 49 | 28 | 30 |
| Edge_Ring | 45 | 33 | 30 |
| Center | 32 | 27 | 30 |
| Random | 35 | 32 | 30 |
| none | 12 | 23 | 26 |
| Near_full | 11 | 14 | 16 |

**在 91 条答不一样的里面**：训练问法答对 **75** 条，考卷问法答对 **9** 条，两个都错 7 条。

**结论**：考卷问法下，模型的答案**塌缩到少数几个类**——30 张划痕只说出 3 张，
同时把大量样本判成 `Loc`（真值 30，判了 56）。

## 五、这算不算"模拟真实环境"？（解释，可能错）

学生最初的假设是：「真实环境下没有 system prompt，所以考卷不带是对的」。

**这个前提多半不成立。** 【解释，属工程经验判断，不是本仓库可核对的事实】

**system prompt 不是用户输入，是应用层写死的。** 真实部署通常是：

```
用户只打「这张图什么缺陷？」
        ↓
程序自动拼成：[系统] 你是半导体晶圆 BIN 图缺陷分析专家…… + [用户] 这张图什么缺陷？
```

用户自己从没打过那句话。所以"有没有 system prompt"**取决于怎么部署**：

- 做成内部工具、开发者在应用层写了提示词 → 真实环境**有**
- 直接开放裸接口给人调 → 可能**没有**

**两种部署都真实存在。** 所以这不是"对不对"的问题，是"**你要测哪一种**"的问题。

## 六、建议（写进新实验方案）

**核心原则：不管真实环境有没有，训练和评测必须一致；而两种场景都该测，分开报。**

| 榜单 | 场景 | 回答什么问题 |
|---|---|---|
| **主榜** | 与训练**完全一致**（带 system、用同样措辞） | "模型学会看图答题了吗" |
| **鲁棒性榜** | 陌生场景（不带 system / 换措辞） | "模型能不能在控制不了的问法下也不崩" |

**两条禁止**：

1. **不要**用"陌生场景"的分数去说明"模型的能力" —— 会**低估**。
2. **不要**用"训练场景"的分数去说明"能不能上生产" —— 会**高估**。

**报分数时必须注明是哪一个场景。**

**顺带**：第二个榜单恰恰是真实生产最关心的，因为**生产环境里的问法你控制不了**。
现在项目只报了第一个场景的一个数字（0.6230），还把它当成"能力"在引用。

## 七、一个连带问题（留给方案讨论）

如果基准改成"两遍都跑"，**已有的历史结果怎么办？**

现在**全部 12 个 run × 16 个指标的每一个数字，都是在考卷问法下测的**。
而训练格式的诊断**只做过 SFT 一个模型**（`results/raw_outputs/` 里只有
`qwen35_9b_adapter_trainfmt.jsonl`，**没有** `qwen35_9b_zero_shot_trainfmt.jsonl`）。

所以：

- 改基准 → **12 个 run 全部要重跑**，否则新旧不可比（这正是 `LIMITATIONS.md` §6.4
  「有意未在运行中途修改，因为修改会使 Base 与 SFT 不再可比」那条规矩的同一个道理）。
- 或者：**保留现有数字作为"陌生场景榜"，另外补一个"训练场景榜"**，两套并存。

**这两个选项需要在方案讨论里定。**
