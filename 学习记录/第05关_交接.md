## 一、这一关讲完了什么

### 1.1 为什么不能"全都改"（显存账）
- **要解决的问题**：为什么单卡训不了 9B（全量微调）
- **核心概念**：训练时显存里要同时摆三样 —— ① 权重 ② 梯度（每个参数一张"该改多少"的纸条）③ 优化器账本（每个参数两本）
- **结论**：按公式算 ≈72 GB（**注意：学生在课上听到的第一版是 108 GB，基于"参数 90 亿"的估算；实测参数量见 1.6，重算后是 ≈72 GB**）> 卡 48 GB → 必须省
- **⚠️ 全程必须标"这是按公式算的，不是实测"**

### 1.2 两招省显存
- **招 ① 量化**：权重从 16 位压到 4 位 → 18 GB → 4.5 GB（按实测参数量重算：12 GB → 3 GB）
  - 真实参数：`--quant_method bnb --quant_bits 4 --bnb_4bit_quant_type nf4 --bnb_4bit_use_double_quant true`（`10_train_qlora.sh:35-39`）
- **招 ② LoRA**：原模型一个参数都不动，只训旁边挂的两个"瘦长条"
  - `lora_A: Linear(4096→16)` + `lora_B: Linear(16→4096)`（模型打印，`08_train.log:625-635`）→ **rank 16 在结构里看得见**
  - `--tuner_type lora --target_modules all-linear`（`:31-32`）
- **QLoRA = Q(量化) + LoRA**，两招绑在一起的原因：4 位存下来的数字算不了梯度，配件替它承担"可训练"
- **⚠️ 未核实项**：QLoRA 论文的第三个技巧"分页优化器"在本 run 里**搜不到对应开关**（`grep paged` 0 命中）→ 只能说"用了其中两个"

### 1.3 真实训练命令：脚本骨架
- **核心代码**：`code/projects/wafer-defect-vlm/scripts/10_train_qlora.sh:1-60`

### 1.4 训练数据长什么样
- **硬证据（磁盘格式）**：`08_train.log:557-560` → `features: ['messages', 'images', 'dataset']`，`num_rows: 12876`
- **硬证据（模板化后的原文）**：`08_train.log:577` 的 `[INPUT]` 那一行 —— 完整可读
  - system = `你是半导体晶圆 BIN 图缺陷分析专家，只依据图像回答，不推测工艺根因。`（`curate.py:35`）
  - user 里 `<image>` 被展开成 **`<|vision_start|>[248056 * 196]<|vision_end|>`**
- **⚠️ `train.jsonl` 原文本机没有**（在服务器 `data/curated_v2/splits/`）。课上讲的那条 jsonl 是**用上面两处证据重建的**，必须标清。
- **图片怎么进模型**：
  - 教师标注走 HTTP → **base64**（`utils.py:239-242` `image_data_url`，调用处 `annotate.py:107`）
  - 训练在本地 → **jsonl 里存的是文件路径**（`curate.py:273` `"images": [image]`），**没有编码**；processor 读图 → 切 patch → `pixel_values [784, 1536]`（`results/reports/template_check.json`）
- **`<image>` 是空位不是内容**：196 个占位符 = 位置；视觉塔算出的 196 个 4096 维特征 = 内容；进语言模型前把空位填上
  - **⚠️ "替换"那一行代码在服务器上的模型实现里，本机没读到** → 讲成"通用机制"，不要讲成"我在本机核实过"
- **`sample_id` / `task` 两列没进 ms-swift**：`curate.py:274-275` 写了这两个键，但日志的 features 只有三个 → **推断是被丢了，标未核实**（同族事实：`LIMITATIONS.md` §8.2 记过"swift infer 不写回 sample_id 而错位"）

### 1.5 loss mask（只对答案算分）★ 本关最重要的一块
- **要解决的问题**：一句话里既有问题又有答案，不能对"问题"也算损失
- **核心证据（原文）**：`08_train.log:578-579`
  ```
  [LABELS_IDS] [-100, -100, …(前 262 个)…, 4754, 727, 431, …]
  [LABELS]     [-100 * 262]{"defect_type":"none", …}<|im_end|>
  ```
- **实测数字**（课上脚本数的）：总长 **393** 个 token；屏蔽 **262** 个；算损失 **131** 个
- **`-100` = PyTorch 的"这个位置跳过、不算损失"约定**
- **那 262 个里最大的一块是 196 个图片 token** —— 图片也要屏蔽（不然模型会学"生成图片"）
- **⚠️ "262 = 196 图片 + 66 提示词"这个拆法里，66 是我按总数减出来的推断**（没有分词器验证到每个 token）
- **答案结尾的 `<|im_end|>` 是算分的** —— 模型必须学会"什么时候停"
- **`loss_scale=default+ignore_empty_think`**（`08_train.log:240`）：空的思考块不算损失 → 与"训练答案里带一个空 ``"、"考试输出前面那个空行"三处对上（**连接是解释，标一下**）

### 1.6 三种数据（一图三题）与 12876 的来源
- **代码**：`curate.py:258-276` `swift_rows()` —— **一次返回 3 个字典**（`:276` 的列表推导）
- **三道题**（`:261-266` 原文）：
  | 题 | 问题 | 答案 | 来源 |
  |---|---|---|---|
  | ① caption | 请描述…形态、位置和尺寸。 | `result["caption_zh"]` | **老师** |
  | ② classification | 请判断…类别，只回答类别名称。 | `record["failure_type"]` | **真值标签** |
  | ③ structured | 请以 JSON 输出… | 9 个字段的 JSON | **混合**（4 个被数学覆盖，`curate.py:250-254`） |
- **⭐ 学生在这里问出的关键问题**："老师只写了一次，怎么变出三道题？"
  - 答案：老师**一次调用产出一个 10 字段 JSON**（`curate.py:16-19` `REQUIRED_FIELDS`），三道题是**从同一份答案里抄三次**（抄不同字段）
  - **硬证据**：`results/reports/teacher_token_stats.json` → 合计调用 **10612 次** ≈ 5315 张图 × 2（两个老师各一遍）→ **不是 ×3**。所以"任务扩展 ×3"零成本
  - 连带事实：题 ① 的答案与题 ③ JSON 里的 `caption_zh` 是**同一段文字**（`:262` 与 `:248`）—— 设计如此
- **12876 的来源（两层算式）**：
  ```
  第 4 关接受 4829 张 → 按 split 分：train 4292 + val 537 = 4829 ✅
  train 4292 × 3 = 12876 条 ；val 537 × 3 = 1611 条 ；合计 14487 = 4829×3 ✅
  出处：results/reports/acceptance.json → checks.curated.tasks_per_example 三个都是 4292
  ```
- **⚠️ 一条纪律**："一图三题"**不是数据增强**（图一张没动）；而且三道题**必须同 split**（`AGENTS.md` §5.5）——它们是从同一条 record 派生的，`curate.py:331` 用 `record["split"]` 决定归属，**天生不可能跑偏**

### 1.9 视觉侧冻结：三处证据
1. **模型结构打印**（`08_train.log:587-614`）：27 层 `Qwen3_5VisionBlock` + `merger`，**全是普通 `Linear`** —— `lora` 出现 0 次、`Linear4bit` 出现 0 次
2. 对照语言侧（`:615+`）：`out_proj / in_proj_qkv / in_proj_z` 都是 **`lora.Linear4bit`** ✅
3. **视觉塔连量化都没做** → 它跑在 bf16 全精度（它占多少显存，**课上没算**）
- **merger 是"对齐层"**：`Linear(4608, 4608) → Linear(4608, 4096)`，输出 4096 = `embed_tokens` 的隐藏维度 ✅ 与 `--freeze_aligner true` 对应
- **"冻结"的机制**：不产生梯度 → 不产生优化器账本 → 省显存；**但照常参与前向（照常看图）**
- **🎁 顺手钉死了 patch 尺寸（三处独立证据）**：
  - `Conv3d(3, 1152, kernel_size=(2, 16, 16), stride=(2, 16, 16))` → **16×16**
  - `merger.linear_fc1` 输入 **4608 = 1152×4** → **2×2 合并**
  - `template_check.json` 的 `pixel_values_shape: [784, 1536]` → 784 = 28×28；1536 = 3×2×16×16
  - 合起来：`448÷16=28 → 784 个 patch → ÷4 = 196 个 token` ✅

### 1.10 模板解码核对（★ 但**一半不属于本关**）
- **属于第 5 关的**：训练前必须解码模板核对（`AGENTS.md` §11）→ 证据就是 `08_train.log:577-579` 那三行（`[INPUT]` / `[LABELS_IDS]` / `[LABELS]`）
- **不属于第 5 关的**：那个"图片 token = 0"的 bug 出在**检索工具** `tools/retrieval_rank.py` → 属于**第 11 关**
  - 出处：`docs/LIMITATIONS.md:862-866`（记在全项目的 §8「已修复的静默缺陷」清单里）
  - 关键事实：直接传字符串给 processor **仍会返回 `pixel_values`**，但 `input_ids` 里没有 `<|image_pad|>`（seq_len 10、视觉 token 0）→ 视觉塔输出无处可去 → 池化向量是纯文本的 → 检索指标无意义，**而返回类型完全正常**
  - 修法（本机代码可见）：`code/tools/retrieval_rank.py:39` 改用 `apply_chat_template`；`:43-49` **硬断言**：没有 `<|image_pad|>` 就 `raise SystemExit("…refusing to write meaningless rankings")`
- **为什么报告里的检索数字是"修好后"的**：随机排序地板 mAP@10 = **0.0330**（`trivial_baselines.json`），SFT 实测 **0.3873**（`qwen35_9b_adapter__report.json`）—— 差 11.7 倍，纯文本向量不可能算出这个数。**⚠️ 这是用数值合理性反推的推断，不是读到"修复早于运行"**
