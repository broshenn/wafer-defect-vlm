### 0.3 名词表（本文首次出现即解释，此处汇总备查）

| 名词 | 一句话解释 |
|---|---|
| **BIN 图 / 晶圆图** | 一片晶圆上每个 die（芯片）的测试结果矩阵。取值 0=无 die、1=好 die、2=坏 die |
| **WM811K / LSWMD** | 公开的晶圆图数据集（81 万片，其中约 17 万片有人工标注的缺陷类别） |
| **lot（批次）** | 同一条产线、同一段时间、同一批原料做出的**一组**晶圆。同批晶圆外观高度相似 |
| **die** | 晶圆上的单个芯片 |
| **SFT** | Supervised Fine-Tuning，监督微调：给标准答案让模型照着学（"抄答案"） |
| **LoRA** | 一种只训练少量"旁挂参数"的微调方法，原模型权重不动 |
| **QLoRA** | LoRA + 把原模型量化成 4bit，进一步省显存 |
| **Adapter / 适配器** | LoRA 训练出来的那份"旁挂参数"文件 |
| **Merged / 合并模型** | 把适配器合并进原模型权重后得到的完整模型 |
| **RL / 强化学习** | 不给标准答案，只给打分器；模型自己答题，按得分调整 |
| **GRPO / GSPO** | 两种 RL 算法。区别在"归一化算在哪个层级"（每个 token 各算 / 整句算一个） |
| **组大小 G** | 同一道题让模型答几遍。GRPO 靠"组内互相比较"来学 |
| **优势** | 你的分比组内平均高多少 —— GRPO 用它决定鼓励还是打压 |
| **零优势步** | 组内所有答案得分完全相同 → 优势为 0 → 这一步什么都不学（白跑） |
| **KL 惩罚** | RL 里的一根"缰绳"：模型偏离 SFT 太远就扣分，防止为了拿分把话说乱 |
| **有效批次** | 模型一次参数更新实际看了多少个样本 = 微批次 × 梯度累积 |
| **微批次 / 梯度累积** | 一次送进显卡几张图 / 攒几次再更新一次 |
| **epoch / step** | 把数据完整过一遍 / 一次参数更新 |
| **loss** | 训练时模型"错得多离谱"的度量，越低说明越贴合训练数据 |
| **配对检验 / McNemar** | 统计方法：同一批题让两个模型分别答，逐题比较，判断差异是不是碰巧 |
| **p 值** | "如果两者真的没差别，出现这么大差异的概率"。通常 < 0.05 才叫"显著" |
| **95% 置信区间（CI）** | 真值大概落在的区间。跨过 0 就表示"分不出高低" |
| **地板 / 基线** | "什么都不看就能拿多少分"。评价模型分数必须有的参照 |
| **恒答基线** | 永远输出同一个值所能取得的最好成绩 |
| **mAP / nDCG / Recall@k** | 检索指标。排得越靠前分越高 |
| **幻觉率** | 模型描述了图上不存在的原因（如"光刻工艺问题"）的比例 |
| **翻转率** | 同一张图被改过（换色/缩放/旋转）之后，模型答案变了的比例 |
| **混淆（confound）** | 一次改动同时动了两个变量 → 无法判断是哪个造成的 |
| **FUSE** | 一种网络文件系统。本项目用的云盘就是 FUSE，创建文件比本地盘慢很多 |

## 1. 摘要：这个项目做了什么、结论是什么

### 1.1 一句话

> **把公开晶圆图数据集做成"带标准答案的课本"，用 QLoRA 微调 Qwen3.5-9B，再用五张冻结的卷子考试；真正有效的是 SFT，强化学习没有带来可验证的提升。**

### 1.2 主结果（全部实测）

| 指标 | Base（未微调） | **SFT** | 变化 |
|---|---|---|---|
| 九类分类准确率 | 0.2143 | **0.6230** | **+0.4087**（配对检验 p ≈ 2.83e-26） |
| 分类 macro-F1 | 0.1347 | **0.6114** | +0.4767 |
| 结构化输出 · 缺陷类别 | 0.2103 | **0.5840** | 超过恒答基线 0.1190 |
| Caption · 要点命中率 | 0.6270 | **0.7540** | +0.1270 |
| **根因幻觉率** | 0.2183 | **0.0000** | **清零** |
| 鲁棒性准确率 | 0.1905 | **0.5622** | +0.3717 |
| 检索 mAP@10 | 0.3236 | **0.3873** | +0.0637（随机排序地板 0.0330） |
| 结构化 · 径向区 | 0.0794 | 0.2640 | **低于恒答基线 0.8333 → 未通过** |
| 结构化 · 尺寸 MAE | 1.2139 | 0.4999 | **差于地板 0.1101 → 未通过** |

**出处**：`docs/FINAL_REPORT.md` §1 与 §6 主表；逐项来源文件见 §7.1 溯源表。

### 1.3 四个必须一起读的限定语

1. **基准的人工双审没有完成** —— 两份评审表（各 252 行）四列全部为空，基准状态是 `draft_pending_human_review`，`gold_withheld: true`。**所有基准分数都建立在这份"待审草稿基准"上。**
2. **`radial_zone` 那一格不能用** —— 它的低分**主要来自标签口径的缺陷**（见 §3.7），不是模型无能；换判据后仍"接近随机"。
3. **Base 的钟点方向 MAE 5.0000 只在 1/252 个样本上算出** —— **应视为未测**，且与 SFT 的 1.6847 **不可相减**。
4. **RL 的判定范围是"分类准确率"这一张卷子** —— 另外四张卷子 RL 也有成绩，但没有做同等强度的检验（见 §6.9）。

### 1.4 RL（强化学习）的结论

- 共 **10 个 RL run**（GRPO/GSPO × 组大小 4/8/32 × 学习率 1e-5/5e-5，另含 2 个种子重复）
- **没有一个 run 显著超过 SFT。** 最好的一个只多答对 **1 道题**（158 对 157，252 题制）
- **学习率调到 5e-5 的那批显著更差**（少答对 14~22 道题）
- 按论文 §8.11 预留的判据：**保留 SFT 为最终模型，不宣称 RL 有效**

### 1.5 RL 没有"失败"，准确的说法是"没有观察到提升"

- **失败** ≠ **没测出好处**。项目明文写道："这**不等于**「GSPO 不如 SFT」或「GSPO 不如 GRPO」"（`docs/FINAL_REPORT.md:168`）
- 在 lr 1e-5 上，GSPO、GRPO 与 SFT **两两都落在噪声内**
- 项目给出了**一个真实的负面结论**：学习率调到 5e-5 时两个算法都退化 → **"差异的来源是学习率，不是算法"**（有跨算法印证）
- **机制层面确实看到了差别**：在唯一"只改一个参数"的对照上，白跑的步数从 32.67% 降到 26.67%（低 6 个百分点）——**但分数上分不开**

## 2. 技术选型与新旧方案对比

### 2.1 主方案（已执行）

| 环节 | 选型 | 说明 |
|---|---|---|
| 基础模型 | **Qwen/Qwen3.5-9B** | 原生带视觉编码器的统一视觉语言模型，**不用纯文本模型替代** |
| 后训练框架 | **ms-swift 4.x** | 阿里 ModelScope。具体 commit 已记录在 `provenance.json` |
| 训练方法 | **QLoRA（4bit + LoRA）** | 冻结视觉侧，只训 LLM 的线性层 |
| 数据格式 | ms-swift 标准 `messages + images` JSONL | 训练模板 `<image>` 交给框架处理 |
| 评测 | **确定性规则判分**（Python），不是大模型打分 | 同一份答案任何时候重算都得同一个分 |

### 2.2 旧方案与它被替换的原因

旧方案（mentor 早期版本、作为历史对照）是：

| 项目 | 旧方案 | 新方案 | 为什么换 |
|---|---|---|---|
| 主模型 | VisualGLM-6B | Qwen3.5-9B | 原生多模态、生态与框架支持更好 |
| 训练 | SwissArmyTransformer / DeepSpeed 自定义 | ms-swift `swift sft` | 自定义训练循环风险高、难复现 |
| LoRA | 手写 LoRA | PEFT LoRA / QLoRA | 少维护、可复现 |
| **Stage 1** | **EVA-ViT 分类损失 + InfoNCE（对比学习）** | **取消** | 见下 |
| 检索特征 | ViT → QFormer → mean pooling | 生成模型最后一层隐状态 mean pooling | 不再维护 QFormer |
| 图像输入 | `<img>` + 32 个 pad token | 交给 ms-swift 的 Qwen3.5 模板 | 视觉 token 数必须按当版框架定 |

**关于被取消的 InfoNCE（这一步最需要解释）**：

InfoNCE 就是 CLIP 那篇论文用的对比损失。旧方案把它放在 Stage 1，用来让视觉特征在向量空间里"同类靠近、异类远离"。

**取消它的理由是"顺序"而不是"它没用"**：

1. 它在 ms-swift 里**没有现成实现** → 想用就得**自己写一个 Qwen3.5 兼容的训练循环**
2. 而它**从来没有做过消融实验**证明它有用
3. 所以：**先把能验证的基线做完，再考虑不能自我验证的部件**

> **注意**：项目**没有**做过"训视觉编码器"或"加 InfoNCE"的消融 —— 所以"训了会不会更好"这个问题，**双向都无证据**（见 §9 未测量清单）。

### 2.3 与参考论文（WaferSAGE, arXiv:2604.27629v4）的关系

论文是公开的同类工作，本项目参考了它的任务设定与部分结论，但**有三处重大差异**：

| | 论文 | 本项目 |
|---|---|---|
| 评测主指标 | **LLM-Judge**（让另一个大模型打分） | **确定性规则**（可重算、无方差） |
| 视觉特征 | 对比学习预训练的 ViT（768 维），用于 **t-SNE + K-Means 聚类去噪** | 用生成模型的**最后一层隐状态**做池化，**训练时没有任何对比学习目标** |
| 标签清洗 | 靠聚类发现"类别内部的错标样本" | 靠**双教师交叉验证 + 几何裁判** |
| RL 提升 | **+0.009**（论文自评"marginal 微小"） | **不显著**（且低设置下显著更差） |

**两边的 RL 结论方向一致**（都只加了零头），但**数字不可直接比** —— 一把是 LLM-Judge 的尺子，一把是确定性规则的尺子。
论文自己也承认它的评测"带有内在方差"（*"evaluation variance inherent in the LLM-Judge mechanism"*）。

**顺带澄清两个容易记混的点**：

- **论文里没有"旋转/翻转图像"这种做法**（原文 grep `rotat` / `flip` 均为 0 处）
- **论文方法里没有用 CLIP** —— CLIP 只出现在它的参考文献里；用 CLIP 式损失（InfoNCE）的是**旧方案**

本项目里的"旋转"是**考试手段**（把卷子转 90° 看模型还认不认得），且位置类金标会**同步旋转**，不是数据增强。

### 3.2 读原始文件的技术坑（为什么需要一段"伪造模块"的代码）

原始 `.pkl` 是十几年前的 pandas 版本写的，里面存的是**重建说明书**：`"去 pandas.indexes.numeric 找 Int64Index"`。而 **pandas 1.0 删掉了 `pandas.indexes` 这个包** → 现代 pandas 直接报 `ModuleNotFoundError`。

**修法**：在内存里**临时把那个包"搭"出来**（`sys.modules` 注入），让老说明书能找到东西。两个细节：

- 映射表把 `Int64Index` / `Float64Index` **映射到现代的 `pd.Index`**
- 其中一个函数名必须**原样保留**（`_new_Index`），**因为这个名字被写进了 pickle 字节流里** —— 改名就解不开

**为什么不用"装一个老版本 pandas"这条路**：老版 pandas **在 Python 3.12 上编译不过**。所以这个选择是被逼的，好处是**代价被限制在一个 103 行的文件里**。

**另一个细节**：读取时用 `encoding="latin1"`。Python 2 时代的字符串是字节串，用 `utf-8` 解会报错（字节非法），用 `latin1` 是**字节到字符的一一映射、无损搬运**。

规则：**每一类单独抽，上限 800 张**；`none` 单独设上限 **400** 张（给正常晶圆留一点，但不能多 —— 否则模型会学成"看到好片也瞎说有缺陷"）；**固定随机种子 3407**。

|---|---|---|---|

| **Donut** | **555** | **555** | **100%（全拿）** |
| Edge_Loc | 5,189 | 800 | 15% |
| Edge_Ring | 9,680 | 800 | 8% |
| Loc | 3,593 | 800 | 22% |
| **Near_full** | **149** | **149** | **100%（全拿）** |
| Random | 866 | 800 | 92% |

| **合计** | — | **5904** | — |

**⚠️ 两个后果（这是后面所有"这一类样本太少"问题的根源）**：

- **800 是"上限"不是"配额"**：`Donut`（555）和 `Near_full`（149）是**把库里所有能用的都拿了**也凑不到 800
- **`Near_full` 全库只有 149 张** → 它在测试集里只能有 16 条、在验证集里只有 6 条 → **这一类的每个指标都建立在极少样本上**（答对/答错一条 = 分数跳 6.25 个百分点）

### 3.4 数据切分：为什么按批次（lot）切，不按行随机切

这是全项目**可信度的地基**。

#### 3.4.1 做法

对**每一个批次名**做一次哈希（SHA256），取前 8 字节转成整数、对 100 取余 → 得到 0~99 的"桶号"：

| 桶号 | 去向 |
|---|---|
| 0–79 | **train（训练，80%）** |
| 80–89 | **val（验证，10%）** |
| 90–99 | **test（测试，10%）** |

**一个批次只会算出唯一一个去向 → 同一个批次不可能被拆到两个集合。**

**为什么用哈希而不是随机数（这一条很重要）**：

```
随机数分法：按"你排在第几个"发号码
   → 加一批新数据、或者换个遍历顺序，后面所有人的号码全变
   → 昨晚的分组，今天重跑就不一样，而且【不报错】

哈希分法：按"你叫什么"发号码
   → 只依赖批次名自身，与顺序、总数、别的批次都无关
   → 任何时候、任何机器、任何人算，结果都一样
```

**实测证据**（用项目真实的 3822 个批次重算，只把遍历顺序反过来）：

| 分法 | 换顺序后**换了集合**的批次数 |
|---|---|
| **哈希** | **0 / 3822** |
| 随机数 | **1290 / 3822（33.8%）** |

#### 3.4.2 为什么必须按批次切

**理由**：同一批次的晶圆出自**同一条产线、同一段时间、同一批原料** → 它们**长得像、毛病也像**。按行随机切，会让"训练时见过的批次"出现在测试里 → **模型不是在认缺陷，是在认批次**。

**证据（实测）**：

| 事实 | 数值 |
|---|---|
| 批次总数 | 3,822 |
| 真批次（≥2 片） | 1,033 个，覆盖 3,115 片 |
| **批次内主导类别占比的中位数** | **1.00**（完全单一类别） |
| **完全单一类别的批次** | **619 / 1033 = 59.9%** |
| ≥0.8 的批次 | 61.4% |
| 同一批次内**矩阵形状完全一致**的 | **1033 / 1033 = 100%** |

**注**：若改成"看全局平均"，会得到 94.9% 这个虚高的数 —— **因为 3,822 个批次里有 2,789 个只装一片晶圆**（一片自成一批，当然"纯"）。这是本项目记录过的一个统计陷阱（先算错、后自己抓出来）。

**量化"泄漏有多大"**（我做的"作弊基线"实验）：只用一个**不看缺陷、只查表和看尺寸**的模型：

| 作弊方式 | 按批次切（现状） | 按行随机切 |
|---|---|---|
| **只看批次名（lot）** | **0.1290** | **0.4416** ← 泄漏 |
| 只看矩阵形状 | 0.4703 | 0.4975 |
| 只看 die 总数 | 0.4669 | — |
| 多数类基线 | 0.1528 | — |
| 九类随机 | 0.1111 | — |

**读法**：按行随机切时，一个**完全不看图、只会查"这批晶圆历史上是什么类别"**的程序能拿 **44.16%**；按批次切之后它掉到 0.1290（退化成多数类）。**这就是按批次切堵住的东西。**

#### 3.4.3 切分的实际比例与两道硬检查

| | train | val | test |
|---|---|---|---|
| 批次数 | 3,065 | 372 | 385 |
| 占比 | 80.2% | 9.7% | 10.1% |
| **样本数** | **4,721** | **594** | **589** |
| 占比 | 80.0% | 10.1% | 10.0% |

**两道检查**：

1. **内联检查**：脚本会算 train/val/test 三对**批次交集**，**非空就直接抛异常终止**（`raise`，不是打个警告）
2. **独立的外部检查器**（`tools/leak_check.py`，185 行）：分开报告**两种泄漏** ——

   - **样本泄漏**：同一片晶圆同时出现在训练集和基准里
   - **批次泄漏**：同一批次的两片落在不同集合

   它的文件开头写着一句关键话：**"样本层面的交集为零是必要的，但不充分 —— 批次也必须不相交。这就是为什么两者要分开报告。"**

**外部检查器实测结果**：`train` / `val` / `grpo` 对基准的样本交集与批次交集 **全为空**、`lots_straddling_splits: {}`、`failures: []`、`passed: true`。

**它还处理了一个"预期内的重叠"**：GRPO 训练集与 SFT 训练集**是故意重叠的**（RL 本来就在训练集上跑）。检查器用一张**白名单**把"预期内的重叠"与"意外的重叠"分开 —— 预期内的**单独记下来并写明理由**（*"GRPO trains on the SFT training split by design"*），意外的一律 fail。

### 3.5 图像标准化

| 规则 | 值 | 理由 |
|---|---|---|
| 颜色映射 | `0 → 黑 [0,0,0]`、`1 → 绿 [0,255,0]`、`2 → 红 [255,0,0]` | 三种状态、三种颜色 |
| 尺寸 | 默认 **448×448** | 见下 |
| 放大算法 | **最近邻（NEAREST）** | **必须**，见下 |
| 格式 | **无损 PNG**（禁用 JPG） | 见下 |
| 人工提示 | **不加**坐标轴、文字、圆圈 | 不给模型任何提示 |
| 一致性 | Caption 生成、训练、验证、测试**用同一个渲染函数** | 否则模型看到的是"不同的图" |

#### 3.5.1 为什么必须用最近邻放大（实测）

这是一张**离散的 BIN 图，不是照片**：每个 die 只有 3 种状态，**不存在"半个红"**。

| 放大法 | 放大后图上**一共有几种颜色** |
|---|---|
| **NEAREST（项目用的）** | **3**（与原矩阵一模一样） |
| BILINEAR（双线性插值） | **5730**（凭空多出 5727 种） |

**BILINEAR 会在红绿边界上算出一圈渐变中间色** → 等于给模型看**原图里不存在的信息**。

**同一个理由也解释了为什么禁用 JPG**：JPG 是有损压缩，**在硬边界上做的是同一件事**（糊出渐变）。

#### 3.5.2 放大到 448 的真正意义（实测数字）

不是"为了让图好看"，也**不只是"统一尺寸"**。核心是**让每个 die 占够像素**：

| | 数值 |
|---|---|
| 原矩阵（常见） | 26 × 26 |
| 放大到 448 后，**一个 die 的像素尺寸** | **448 ÷ 26 ≈ 17.2 px** |
| 模型视觉编码器的 **patch** 尺寸 | **16 × 16 px** |
| 合并 2×2 后的视觉 token | 32 × 32 px |
| **实测视觉 token 数** | **196 个**（28 × 28 = 784 个 patch，再 2×2 合并） |

**校验**：`448 ÷ 16 = 28`、`28 × 28 = 784`、`784 ÷ 4 = 196` ✅ 与模板实测一致（另有 `seq_len 218`、`image_pad_tokens 196` 的记录）。

**读法**：**die 的像素尺寸（17.2）与 patch 的尺寸（16）处在同一量级** —— 每个 die 都能在特征图上留下自己的痕迹。
如果只缩到 64×64（一样是"统一尺寸"），一个 die 只有 2.5 px，**一个 patch 会盖住大约 6 个 die** → 模型看到的是"一团红绿混杂"。

**诚实的边界**：die 边界（17.2）与 patch 边界（16）**对不齐**，大多数 patch 会稍微跨到隔壁 die —— 所以"一个 patch 完整盖住一个 die"是**不准确**的说法，本项目已作更正。

**关于"拉伸会不会把圆拉成椭圆"**：不会。虽然渲染是"无脑拉成正方形"，但**非正方形矩阵多出来的行列全是 0（没有 die）**，拉伸只作用在空白边上。实测：所有非正方形矩阵（占 84.3%）画出来的图，"非黑区域"外接矩形宽高比**全部是 1.00**。

#### 3.5.3 去噪：只改数字，**不改图**

规则：**一个坏点（值为 2）如果周围 8 个邻居都不是坏点 → 判为测量噪声 → 改成好片（值 1）**。

**关键设计：图像用的是原图，去噪只影响"计数类"数字。**

实测（本报告贯穿全程的那张样本 `wafer_00000096_002`）：

```
raw_defect_count        126   ← 原图有多少坏点
defect_count            114   ← 去噪后还剩多少
filtered_points_removed  12   ← 去掉了 12 个
defect_ratio        0.2139   ← 114 / 533（有效 die 数）
```

**三个数全部保留、一个都不覆盖** —— 因为这样"这个去噪决定"将来**可以被人推翻、重算**。项目原则原话：**"去噪版本和原始版本必须分别保存，禁止静默覆盖。"**

### 3.6 几何特征：21 个数字是怎么算的

**全部是纯数学计算，没有任何模型参与。** 大模型要到 §3.9（教师标注）才出场。

#### 3.6.1 先建立坐标系

每片晶圆的矩阵尺寸都不一样（全库有 **248 种**形状），所以**不能用"第 15 行第 8 列"描述位置**。做法：

1. **拟合圆心与半径**：取晶圆**最外轮廓**上的点，用**最小二乘**解圆方程

   数学上是一个小技巧：把圆方程 $(x-a)^2+(y-b)^2=r^2$ 展开移项，变成 $x^2+y^2 = Ax+By+C$ —— **一个线性方程**，未知数只有 3 个，用最小二乘一次解出，再反解圆心与半径。

2. **把所有坐标归一化**（单位 = 半径）：

   ```
   x = (列号 − 圆心x) / 半径
   y = (圆心y − 行号) / 半径      ← 注意行号是往下增大的，所以要减反
   radial = 到圆心的距离（单位：半径）     0 = 圆心，1 = 最外圈
   angle  = 从 12 点起、顺时针的角度
   ```

   **角度**用 `arctan2(x, y)`（注意两个参数**调换**）→ 结果是"**0 = 12 点钟方向，顺时针增加**"，一行代码解决钟点方向，不用分象限判断。

3. **拟合圆心用的是原图、不是去噪后的图** —— 因为**晶圆轮廓在最外圈，噪点在内部**，去不去噪对轮廓毫无影响。

#### 3.6.2 21 个特征的清单

| 类别 | 字段 | 怎么算 |
|---|---|---|
| **计数（5）** | `valid_count`（有效 die 数）· `raw_defect_count` · `defect_count` · `filtered_points_removed` · `defect_ratio`（= defect_count ÷ valid_count） | 数数 + 相除 |
| **位置（6）** | `wafer_center_xy` · `wafer_radius` · `centroid_xy_r`（缺陷坐标的平均=质心） · `centroid_radius_r` · **`radial_zone`** · `clock_sector`（缺陷最多的那个 1/12 扇区） | 拟合 + 求平均 + 分带 |
| **尺寸（2）** | `defect_extent_r`（横/纵跨度取大者，单位=半径） · `radial_span_r` | 最大值 − 最小值 |
| **分布（6）** | `radial_density`（半径 0~1 分 10 个环，按环面积归一化 → 10 个数） · `angular_probability`（12 个扇区占比 → 12 个数） · `mean_radius_r` · `std_radius_r` · `resultant_length`（角度集中度：0=四面八方，1=全挤一个方向） · `angle_entropy_bits`（角度混乱度/熵） | 分环、分扇区统计 |
| **形状（1）** | `anisotropy_min_over_max`（协方差矩阵两个特征值取小÷大：**0 = 一条线，1 = 一团圆饼**） | 特征值 |
| **状态（1）** | `status`：`ok` / `filtered_empty`（去噪后一个缺陷点都不剩）/ `no_defect` | 显式状态码 |

**实测状态分布**：`ok` 5902 张、`filtered_empty` 2 张。

**分母注意**：`defect_ratio` 的分母是**晶圆内的有效 die 数**，不是整个矩阵面积 —— 这是项目明确修正过的旧代码问题。

**汇总中的哪几个会变成"训练答案"**：`failure_type`（真值类别）+ `radial_zone` + `clock_sector` + `defect_extent_r` 这 **4 个**会被当作"数学金标"直接写进训练答案；其余用于质检、评测判分与异常检测。

### 3.7 ⚠️ 重点：`radial_zone` 字段的标签退化（本项目最重要的一项缺陷）

> 这一节解释"为什么某一格分数不能读"。**如果只读本项目的一个技术细节，请读这一节。**

#### 3.7.1 现象

那个字段回答一个问题：**缺陷主要长在"中心 / 中间 / 边缘"**。判据是：

```
< 0.35  → "center"（中心）
< 0.72  → "middle"（中间）
否则     → "edge"（边缘）
```

**喂进去的是"缺陷质心的半径"** —— 也就是**所有坏点坐标的平均值**离圆心有多远。

#### 3.7.2 为什么这是错的（算术层面）

**只要缺陷是"绕着一圈"分布的，它的平均位置必然落在圆心。**

用最简单的算术验证（边缘上两个点）：

```
左边缘 (-1, 0)，右边缘 (1, 0)
平均 = ( (-1+1)/2 , (0+0)/2 ) = (0, 0)  ← 圆心
```

再加上下两个点，四个点平均仍然是 `(0, 0)` —— **左右抵消、上下抵消，对称的东西平均下来归零。**

**所以任何"绕圈型"图案都会中招**：边缘环、随机散布、满片、环形 —— 它们的**质心全在圆心附近**，于是**全被判成 `center`**。

#### 3.7.3 实测（全库 5904 张）

| 真值类别 | 质心半径中位 | **平均半径中位** | 判 `center` | 判 `edge` |
|---|---|---|---|---|
| **Edge_Ring（边缘环）** | **0.051** | **0.939** | **97%** | **0%** |
| Random（随机散布） | 0.051 | 0.688 | **100%** | 0% |
| Near_full（近乎满片） | 0.038 | 0.685 | **100%** | 0% |
| Donut（环形） | 0.115 | 0.569 | 99% | 0% |
| Center（中心） | 0.079 | 0.630 | 99% | 0% |
| Edge_Loc（边缘局部） | 0.292 | 0.828 | 63% | 3% |
| Loc | 0.238 | 0.721 | 71% | 5% |
| Scratch | 0.229 | 0.757 | 74% | 1% |
| none | 0.177 | 0.785 | 85% | 1% |

**三个发现，一个比一个严重**：

1. **`edge` 这个判定几乎从不出现** —— `_zone()` 写了三个分支，**第三个基本是废的**（九个类里最高只有 5%）
2. **几乎所有东西都被判成 `center`** —— 这个字段**退化了**，不再区分任何东西（其中最极端的：`Edge_Ring` 的缺陷**平均在 0.939 个半径处**，也就是贴着最外圈，却被记成"中心"，97% 如此）
3. **它与真值类别基本脱钩**

#### 3.7.4 后果链（为什么它是"雷"而不是"小 bug"）

```
① 字段本身算错
        ↓
② 污染【训练答案】：这个字段是"数学金标"直接写进答案的
   → 训练答案里 center 占 85.6%（4547/5315）—— 是【整类】地错，不是偶尔错
        ↓
③ 污染【评测金标】：评测金标读的是同一个数字
   → 金标里 center 占 83.3%（210/252）
   → 于是"永远回答 center、完全不看图"就能拿 0.8333【这就是 0.8333 的来历】
        ↓
④ 那一格分数读不通：SFT 只有 0.2640，比"什么都不看"还差
   → 但这【不能】读成"模型没学会"——标准本身坏了
```

**最要命的地方是"自洽"**：**同一个数字，既当标准答案，又当评分标准。**

```
训练时：教你输出 "center"
考试时：评分标准说必须是 "center"
   → 学生若完美学会 → 该字段接近满分
   → 而它其实是错的
   → 但没有任何东西会报警 —— 训练和评测一起错
```

**普通 bug** 会产出"看起来就不对"的东西；**这个 bug 产出一个内部完全自洽的世界**，只能靠**外部事实**（真值类别、视觉直觉）才能发现它错了。

#### 3.7.5 项目的复核（换了三种判据重打分）

| 判据 | 金标多数类占比（= 恒答水位） | Base | SFT |
|---|---|---|---|
| 质心（现状） | **0.8333** | 0.0794 | 0.2640 |
| **平均半径**（缺陷像素平均离圆心多远） | **0.5079** | 0.1310 | **0.4560** |
| 外沿半径 | 0.9960 | 0.1706 | 0.4200 |

**换判据后**：水位从 0.8333 掉到 0.5079，SFT 从 0.2640 升到 0.4560。

**但 SFT 仍然 0.4560 < 0.5079 —— 仍未过线。** 且 `mean_radius` 只有两个取值，**随机水平就是 0.5**。

**项目给出的定性（原话）**："**接近随机**，既非「学会」也非「远差于不看图」。"

#### 3.7.6 附带发现：**结构性不可评分**

评测提示词让模型从 `center|middle|edge|full|none` 五个值里选，**但金标里 `full` 出现 0 次**（训练答案里也没有 `full`）。
**而 SFT 有 69/250 次回答了 `full`** —— 这些答案**在构造上不可能得分**。

#### 3.7.7 这个 bug 为什么能活下来（一个方法论级的教训）

**测试亲手把它藏起来了。** `tests/test_curate_arbitrate.py` 里那个仲裁测试：

```python
rec = record("Edge_Ring", radial_zone="edge")   # ← 手工把 "edge" 注入记录
wrong = {"radial_zone": "center", ...}          # ← 它知道 center 是【错】的
right = {"radial_zone": "edge",   ...}          # ← 它知道 edge 是【对】的
assert geometry_verdict(rec, right, "radial_zone")
assert not geometry_verdict(rec, wrong, "radial_zone")
```

**测试完全知道正确的期望**（它把 `center` 标成"错"、把 `edge` 标成"对"），
**但它从头到尾没有调用过真正算这个字段的那个函数** —— 它喂的是**自己造的数据**。

| | |
|---|---|
| 测试**测了** | **怎么用**这个字段（仲裁逻辑会不会采纳几何答案） |
| 测试**从没测** | **这个字段是怎么算出来的** |
| 后果 | 真实管线给出 `"center"`，测试自己造的是 `"edge"` → **测试永远通过** |

**教训**：**"测试通过" ≠ "被验证过"。一个喂自己造的数据的测试，验证的是它自己。**

**修法方向**：用**真实输入**（一张已知是边缘环的图）跑一遍特征计算，断言它返回 `edge` —— 而这正是它一直缺的东西。

#### 3.7.8 这个 bug 的影响范围（已逐指标排查）

| 指标 | 受影响？ |
|---|---|
| 九类分类 0.6230 | ❌ 不受影响（用的是真值类别字段） |
| 结构化 `defect_type` 0.5840 | ❌ 不受影响 |
| **结构化 `radial_zone` 0.2640** | ✅ **整格受影响** |
| 结构化 `clock_sector` / `size_r` | ❌ 用的是别的字段（它们各有自己的问题） |
| **Caption（要点命中率、幻觉率）** | ❌ **不受影响** —— 评分规则里**存了** `check_radial_zone`，但**评分器从来没有读它** |
| 鲁棒性、检索 | ❌ 不受影响 |

**所以：主结论不受影响；一个字段的分数整格作废。**

**另需注意（新发现）**：换判据的那次复核**只覆盖了 Base 与 SFT 两个模型**，10 个 RL run 那一列全部是 `not run` —— 所以"RL 在这个字段上比 SFT 高"这类话，**是站在未修正的判据上说的**。

### 3.9 教师蒸馏：请大模型写"过程"

#### 3.9.1 问题是什么

我们手上的标签**只有一个类别词**（Donut / Scratch / Center…）。但要教会模型"看懂一张晶圆图"，需要的是：**缺陷在哪、什么形状、多大、朝哪个方向、以及一段自然语言描述**。

**这些没人标过** → 花钱请大模型来写。

#### 3.9.2 三条铁律

1. **只给训练集和验证集（5315 张）写** —— **测试集 589 张一张都不给老师看**
   （理由：老师看过考卷就会**把答案写进课本**，学生背下来就是"假会"）
2. **两个老师交叉** —— 一个老师说的话无法验证；两个老师不一致的地方**恰好是最可疑的地方**
3. **不硬选** —— 不一致时先用**数学裁判**，连裁判都判不了才隔离

#### 3.9.5 打分与筛选（"置信度"是**算出来的**，不是老师自报的）

每个答案从 **100 分**开始扣，扣到什么分就是什么分；**及格线 60 分，且不能有硬失败**：

| 扣分项 | 扣多少 | 性质 |
|---|---|---|
| 类别与真值不符 | **−50** | **硬失败（直接毙）** |
| 缺字段 | 每项 −5（最多 −40） | **硬失败** |
| 径向区对不上 | −15 | |
| 形态可疑 | −15 | |
| 钟点方向差超过 1 格 | −15 | |
| 尺寸越界 | −15 | |
| 描述为空 | −35 | |
| **描述里出现"污染/光刻/蚀刻/设备故障"等根因词** | **−25** | **防幻觉** |
| 老师自己标了"不确定" | −20 | |

**为什么不用"老师自称的置信度"**：模型自报的置信度不可信（它会自信地胡说）。这套分数**完全由规则算出、可重算**。

#### 3.9.6 答案的三个来源（这是"数学金标 + 教师模型"的落地）

**同一张图，学生会得到 3 道题，每道题的答案来源不同**：

| 题目 | 答案从哪来 |
|---|---|
| ① **描述**（形态、位置、尺寸） | **教师模型写的中文描述** |
| ② **分类**（九选一） | **真值标签** —— 老师说的不算 |
| ③ **结构化 JSON**（7 个字段） | **混合**：4 个字段用数学金标覆盖，其余用老师 |

**第 ③ 题的混合逻辑（代码层面）**：

```
if geometry_gold:                      # 这个开关当时是开的
    target["defect_type"]     = record["failure_type"]        # 真值标签
    target["radial_zone"]     = features["radial_zone"]       # 数学
    target["clock_direction"] = features["clock_sector"]      # 数学
    target["size_r"]          = features["defect_extent_r"]   # 数学
# 其余（shape / density / continuity / caption_zh / caption_en）保持老师写的
```

**代码注释给了理由**：这四个字段**是评测时拿客观数据判分的**；如果老师的答案与客观数据矛盾，等于
**训练学生去丢掉它将来会被打分的那个指标**。
一句话：**能算的用数学，能查的用真值，只有算不出也查不到的（描述、形态、密度），才让老师写。**

## 4. 训练（第二阶段）：QLoRA 微调

> **入口命令**：`bash scripts/10_train_qlora.sh`
> **产物**：LoRA 适配器 `qwen35_9b_qlora_v1`

### 4.1 为什么要 QLoRA：先把显存账算出来

"训练"的意思是**改动模型里的数字**。Qwen3.5-9B 有几十亿个数字。全量微调要存：

| 要存什么 | 大小 |
|---|---|
| 权重（BF16） | ≈18.0 GB |
| 梯度 | ≈18.0 GB |
| 优化器状态（Adam） | ≈72.0 GB |
| **合计** | **≈108 GB** |
| **我们的显卡** | **48 GB（RTX 4090）** |

**差一倍多，塞不进去。** 所以要用两招省。

### 4.2 招一：量化（把数字从 16 位压成 4 位）

```
权重：≈18 GB → ≈4.5 GB   （省约 4 倍）
```

实际配置：`bnb` 4bit + `nf4`（一种为近似正态分布权重设计的 4bit 格式）+ `double quant`（对量化常数本身再量化一次，再省一点）+ 计算时用 bfloat16。

**为什么 4bit 不会把模型搞坏得太厉害**：模型权重是很"密集"的一堆小数，4bit 保留了它们的**相对大小关系**；而 LoRA 的存在又让"真正要学的新东西"走的是另一条更高精度的路（见下）。

### 4.3 招二：LoRA（原模型一个数字都不动，只训"小配件"）

**原理**：原来一层有个大矩阵 W（例如 4096×12288 ≈ 5000 万个数字）。LoRA **不碰它**，而是在旁边挂两个"瘦长条"：

```
A（16 × 4096）→ B（12288 × 16）       两个加起来只有约 26 万个数字
计算变成：  结果 = W·x + B·A·x
              ↑ 冻住     ↑ 只更新这两个
```

**比喻**：**给一台已经调好的机器加一个微调旋钮** —— 不动机器本身，只拧旋钮。

**本项目参数**：

| 参数 | 值 | 说明 |
|---|---|---|
| LoRA rank | **16** | 配件的"宽度"（低秩的秩） |
| LoRA alpha | **32** | 配件的影响力缩放（经验上取 rank 的 2 倍） |
| `target_modules` | **all-linear** | 所有线性层都挂配件 |
| dropout | 0～0.05 | 轻微正则 |

**等效换算**：我们要训的参数从"几十亿"降到"**4327.83 万**"，占比 **0.7220%**。

### 4.4 视觉侧整个冻住（`freeze_vit` / `freeze_aligner`）

```bash
--freeze_vit true        # 看图的那部分（视觉编码器）完全不动
--freeze_aligner true    # 图→语言的转换器（对齐层）也不动
```

**为什么**：

1. **它已经会看图了** —— 形状、颜色、位置它都看得见；我们要教的是"晶圆这件事"，不是"怎么看图"
2. **这两层最容易训崩** —— 数据量不大时动了它，可能把原有的视觉能力破坏掉
3. 这是**风险最低**的起点：先把"冻结视觉侧"这条基线做扎实，再谈别的

**⚠️ 因此实际只训了 LLM 侧的线性层。**

**"没训视觉侧"这件事的证据与代价**（在 §5.10 详述）：换色实验掉分最狠（−12.3 个百分点），而颜色是**冻结的视觉塔**给的特征 —— 我们没机会教它"颜色不是判据"。

| 峰值显存 | **32.92 GiB / 48 GiB** |

**检出点（checkpoint）的选择规则**：**预先规定**、而不是事后挑最好看的 —— `checkpoint_choice.json` 记录了 7 个评估点，loss 从 **0.4692 → 0.2800 逐点单调下降**，据此选定；报告明确"禁止只汇报最好 checkpoint，需要记录选择 checkpoint 的预先规则"。

**⚠️ 一句必须记住的话**：**loss 低 ≠ 模型好。** loss 只说明"课本背得熟"；它好不好要去**考卷**上看（第 5 节）。

**"课本分"与"考卷分"的单位不同，不能相减**：

- **课本分**（`eval_token_acc` 0.9026）—— **按"字"算**（预测的每个 token 有多少比例对）
- **考卷分**（分类准确率 0.6230）—— **按"张"算**（整张图的类别答对的比例）

**要比的是"同一张卷子上，训练前 vs 训练后"。**

### 4.8 训练数据的形态与 loss mask

**每行是一条多模态对话**（`messages + images`）：

```json
{"messages":[
   {"role":"system","content":"你是半导体晶圆缺陷分析专家。"},
   {"role":"user","content":"<image>\n请描述晶圆图中的主要缺陷形态、位置和尺寸。"},
   {"role":"assistant","content":"一个致密的环形缺陷簇，位于晶圆边缘，宽度约为0.1R。"}],
 "images":["data/images/wafer_xxx.png"]}
```

**关于 `loss mask`（为什么要专门检查它）**：

训练时**只应该对"回答部分"算 loss**，不应该对"题面部分"算 loss。如果掩码写错，模型会被训练去"预测问题本身"，训练 loss 照样下降但学到的东西是错的。

所以项目在训练前**抽样解码了 ms-swift 的模板**，确认三件事：`<image>` 位置正确、labels 掩码正确、回答部分正确 —— 这一步被列为**训练前的强制检查**。

**训练侧约束**：同一张图的**原图、去噪图、旋转图、双语 Caption、所有问答，必须留在同一个集合**（防止变体跨集合泄漏）。实测：`train_examples 12876 = 4292 × 3` —— **多一张都会破坏这个等式**（也说明训练集里**一张扰动图都没有**，见 §5.10）。

### 5.2 卷子是怎么挑出来的

#### 5.2.1 取样规则

- **只用测试集**（`split = test`），实测：252 条**全部**来自 test（test 总共 589 张）
- **每类上限 30 条**，但库不够就全拿：`Near_full` 只拿到 **16** 条、`none` **26** 条

#### 5.2.2 隔离验证（实测）

- 卷子 252 条 ∩ 训练集 = **空**；∩ 验证集 = **空**
- 卷子的 202 个批次 ∩ 训练集批次 = **空**
- 外部检查器：`sample_overlap_with_benchmark` / `lot_overlap_with_benchmark` 三项全空、`failures: []`、`passed: true`

#### 5.2.3 ⚠️ 一个已记录的隐患：难度分这块地方"分辨力很弱"

项目的取样靠一个"难度分"，但**这个分数实际上几乎没有区分能力**：

- **其中一条规则（"孤立噪点数"）在 91.9% 的样本上是常量** —— 因为它把"删掉 ≥5 个噪点"截顶为满分，而大多数类别 100% 的样本都满足
- **其中另一条规则（给四类各 +0.5）对"选了哪 252 条"零影响** —— 因为取样是**先按类别分组、再在组内排序**，而这条规则对**同一类别内所有样本加同一个常数**，等于整列平移，不改变组内顺序。（实测：把这条规则整条删掉重跑，选出的 252 条**完全相同，差集 0 条**）
- **结果是"分数取值种数极少"**：例如 `Center` 的 90 个候选里只有 **3 种**分值，其中最大的一档占了 **78 张（87%）** → 同分档内只能靠哈希抽签决定谁入选
- **实测后果：只改随机种子，选出的 252 条会换掉 84~98 条（约 1/3）**

| seed | 与当前 252 条相同的条数 |
|---|---|
| 1 | 161 / 252（63.9%） |
| 42 | 159 / 252（63.1%） |
| 3408 | 165 / 252（65.5%） |
| 99999 | 168 / 252（66.7%） |

**怎么读这件事**：

- **① 事实**：难度分在"典型"那一端**滑成了抽签**；"难"那一端是可靠的（高分样本稀少）
- **② 解释**：所以这份 252 条**不是唯一合理的一份**；但这**不影响已发布结果**（基准已按 `seed=3407` 冻结并生成 773 个文件的哈希）
- **③ 未测量**：**这个种子敏感性对结论的影响从没被测过**（验证方法：用第二份种子出的基准跑同一批模型，看结论是否一致 —— **未做**）

### 5.5 判分的是一个 Python 程序，不是人、也不是大模型

**项目里确实写了"让大模型当评委"的提示词，但从未被调用过。**

**判分程序的四步**（`src/wafer_vlm/evaluate.py`，316 行）：

1. **剥掉思考块** —— 不剥的话，`normalize_label` 会看到 `"\nScratch"`，**每一道分类题都会被判成无效**（代码注释原文）
2. **抠出答案文本** —— 挨个试 `response` / `prediction` / `output` / `choices[0].message.content` / `messages`
3. **贴回题号** —— **因为 ms-swift 的输出不带 `sample_id`**，必须按顺序对齐
4. **逐卷判分**

**五张卷子各自的判法**：

| 卷子 | 判法 |
|---|---|
| ① 分类 | **词表内精确相等**；不在词表的记 `INVALID`（**不混进"答错"**）；macro-F1 用 **bootstrap 500 次**给 95% 置信区间 |
| ② 结构化 | 抽出 JSON（抽不出记 `parse_errors` 并跳过）→ 类别、径向区**逐字段相等**；**钟点用环形距离**（`min((预测−金标)%12, (金标−预测)%12)`）；**尺寸用绝对误差** |
| ③ 描述 | **关键词命中率 / 关键词违规率**（纯字符串包含，**无语义理解**） |
| ④ 鲁棒性 | `accuracy`（对真值）+ **`flip_rate_vs_clean`**（对**同一张图干净时的答案**） |
| ⑤ 检索 | `mAP@k` 用**二值相关**（相关/不相关）、`nDCG@k` 用**分级相关**（2/1/0） |

### 5.8 为什么有两格读不通（这一节是评测方法论的核心）

#### 5.8.1 `radial_zone`：标签坏了

见 §3.7（完整因果）。**结论**：这一格**只能用来评价标签，不能用来评价模型。**

**⚠️ 补充一条新发现**：换判据的那次复核**只覆盖了 Base 与 SFT**，10 个 RL run 全是 `not run`
→ **RL 在这个字段上的分数（0.2460～0.4603）从未在修正后的判据下重评过。**

#### 5.8.2 钟点方向：**未测**，且两者不可比

Base 的 `5.0000` 是**只在 1 个样本上算出来的**（99.6% 的答案解析失败被跳过）。

**计分覆盖面（可核对）**：Base **1/252**（丢弃 251）· SFT **203/250**（丢弃 47）· GRPO **198/252**（丢弃 54）。

**被丢弃的答案**是 `all` / `none`（模型说"整个圆都有"或"没有方向"），而且**丢弃不是随机的**：

- `Random` 类的丢弃率 **0.80**
- `Edge_Ring` 类的丢弃率 **0.60**

**恰恰是"单一钟点方向本就没有意义"的两类图案。**

**两个后果**：

1. SFT 的 1.6847 是**条件于一个更容易的子集**算出来的 → **真实值应该更差**（这是**幸存者偏差**）
2. **SFT 与 GRPO 的 MAE 不能相减**，因为两者丢弃的是**不同的子集**

### 5.10 鲁棒性（第四张卷子）

**怎么考**：252 张各生成 **3 个变体 = 756 张**

| 变体 | 做法 |
|---|---|
| `resize_224` | 448 → 224（**最近邻**） |
| `recolor_v1` | 绿 `(0,255,0)→(0,180,30)`、红 `(255,0,0)→(255,80,80)` |
| `rotate_90_ccw` | 逆时针 90°（**最近邻，不插值**） |

**金标处理**：**类别不变**（`gold_transform.class_unchanged: true`），**但钟点方向跟着转**（旋转会改变方向，标签必须同步旋转，不能沿用原方向）。

**判两个数**：准确率（对真值）+ **翻转率**（对同一张图干净时的答案）。

| 变体 | Base 准确率／翻转率 | SFT 准确率／翻转率 |
|---|---|---|
| （干净） | 0.2143 | 0.6230 |
| recolor | 0.1865 / 0.1230 | **0.5000 / 0.2857** |
| resize | 0.1706 / 0.1389 | 0.5635 / 0.2381 |
| rotate | 0.2143 / 0.1548 | 0.6230 / 0.2183 |

**三个可核对的现象**：

1. **换色掉分最狠（−12.3 个百分点）、旋转几乎不掉（±0）** → 模型的判据里"**颜色**"权重不小
   （逐类别看：Center −33.3 · Random −23.3 · Edge_Ring −16.7 · Edge_Loc −10.0 · **Near_full −75.0（只 16 条）** · none **+34.6（未解释，不算结论）**）
2. **`resize_224` 正好撤销了"放大到 448"的努力** —— 448 时 die 是 17.2 px；224 时只有 8.6 px → **一个 patch 跨约 2 个 die**
3. **训练集里一张扰动图都没有**（`12876 = 4292 × 3` 这个等式一破就说明混进了别的）

**"没训视觉侧"的三处代价（推测 + 未测量）**：

- **颜色是冻结的视觉塔给的特征** —— 我们没机会教它"颜色不是判据"
- 数据增强**没做**（训练集里一张扰动图都没有）
- **⚠️ 但"到底是哪个的锅"分不清**：三个成因都在，**项目没做任何消融**
  → **"训了视觉侧 / 加了增强会不会更好" = 未测量**

**⚠️ 翻转率不能跨模型直接比**：Base 在 252 条里**有 185 条（73%）都答 `Random`** ——
**一个反复答同一个词的模型，翻转率天然低**（它"没东西可翻"），那不是"稳"。

**⚠️ 视觉侧训练的四条门禁判据里没有"鲁棒性"** —— 而鲁棒性恰恰是"冻结视觉塔"最可能暴露的地方（这是我们的观察，不是项目结论）。
另外：**"视觉侧适配"这一步从未被正式评估**（脚本存在、无运行记录、缺席也没进任何未决清单）。

### 5.11 检索（第五张卷子：以图搜图）

#### 5.11.1 为什么单独一张卷子

项目原则（宪章 §9）：**生成能力 ≠ 检索能力**。
Qwen3.5 的生成式微调**不会自动保证**视觉向量适合检索，所以必须单独测。

#### 5.11.2 题目、答案、规模

| | |
|---|---|
| **题目** | **就是图本身**（90 张"拿来找的图"） |
| **图库** | **252 张固定不变**（就是核心卷子那 252 张） |
| **答案** | 一张**相关性表**（22505 行）：每行 `{query_id, gallery_id, relevance}`，2 = 很像 / 1 = 同类但不像 / 0 = 不像 |
| **规模（实测）** | 90 × 252 = **22680** 对，**扣掉 175 对**（90 个"自己" + 85 个"同批次兄弟"）→ **22505** 对 |
| | 每张平均 **250.06** 个候选 |

#### 5.11.3 🔑 检索时模型**不用 `generate()`**（这是最容易误解的一点）

检索工具（`tools/retrieval_rank.py`，105 行，**全文没有一次 `generate`**）做的是：

```python
PROBE = "Describe the defect pattern in this wafer map."
out = model(**inputs, output_hidden_states=True)      # 跑一遍前向
hidden = out.hidden_states[-1].float()                # 取最后一层
pooled = (hidden * mask).sum(1) / mask.sum(1)         # 平均池化
normalize(pooled, dim=-1)                             # 归一化
```

**一句话**：喂「图 + 那句固定的话」跑一遍前向，**直接掏内部状态**；**模型接下来会写什么，不看、丢掉**。

- 实测序列：分类模板总长 **251**、其中视觉 token **196** → 向量里约 **78% 是视觉 token**
- **同一句提示词是硬要求**（那句话约 22% 混在向量里）；**换提示词会怎样从未测过**
- **🔒 硬断言**：没有 `<|image_pad|>` 就**直接终止**（*"refusing to write meaningless rankings"*）—— 因为曾经出现过"图根本没进模型、池化出来是纯文本向量、而返回值看起来完全正常"的事故

**与 CLIP 的区别**：CLIP 是双塔 + 对比学习；这里是**拿生成模型的隐状态顺手当向量**，**训练时没有任何对比学习目标**。

**排序**：归一化后点积 = 余弦相似度 → 降序 → **排除自己 + 排除同批次** → 取前 50。

#### 5.11.4 分数与一个讲得通的真实例子

地板 **0.0330** → Base **0.3236** → SFT **0.3873**（最好的 RL run 0.4337）。

**用真实例子讲通"检索在比什么"**：

- 搜索词 `wafer_00023639_020`（真值类别是 **Center**）
- 模型（Base 与 SFT **都是**）把 `wafer_00017134_013`（真值 **Donut**）排在第 1 名
- **看图就懂了**：搜索词是"绿底中间一团红"，第 1 名是"红环包着一块绿心" —— **空间布局像，但红绿对调**
- **所以模型看的是"像素布局的像"，而标准答案是"标签的像"**
- 该搜索词前 10 名里只有 **1（Base）/ 2（SFT）** 个是真正相关的

#### 5.11.5 为什么**不能**宣称"SFT 优化了检索"

两个理由：

1. **训练时没有任何对比学习目标** → 检索的提升是**副产品**
2. **检索那一列走 merged 模型，生成那列走 adapter**（两条载入路径）

**⚠️ 另外**：`G=32 检索最好`这个说法**已不成立** —— 它只在 `mAP@10` 上居首，`nDCG@10` 与 `Recall@10` 都不是第一。**"三项里只有一项是最高"不能支撑"它重塑了表征"这个结论。**（这是本项目被实测推翻的又一处"把点估计极值当结论"。）

### 5.12 Adapter 与 Merged 的等价性（第八关）

**问题**：同一个模型有两种用法 —— ① 原模型 + 适配器；② 把适配器合并进主模型的权重。**按道理答案应该基本一致。**

| 对比 | 完全一致 | 功能一致率 |
|---|---|---|
| **adapter vs merged**（60 行） | 28 / 60 = **0.4667** | 0.7667 |
| **同一个模型、只换计算精度**（同 60 行） | 26 / 60 = **0.4333** | 0.7000 |

**关键在这一句话**（`equivalence.json` 自己的说明）：

> *"exact_agreement is a numeric-reproducibility measure, **not a correctness one**: the same model at a different precision does not reach 1.0 on free-form answers. **Compare functional_agreement against the same-model precision floor before concluding the merge changed behaviour.**"*

**读法**：单独的 `0.4667` 看起来像"合并改变了模型行为"（一半答案都变了）；但**同一个模型只换精度就只有 0.4333** → **0.4667 与那个地板几乎没有差别**。

**结论**：**merge 没有改变行为**；验收标准"Adapter 推理和合并后推理结果基本一致"**按项目自己的判据是通过的**。

**⚠️ 一个报告层面的缺陷（我们发现的）**：`FINAL_REPORT` §6b **只写了 0.4667 这一行，没有引用同目录下的 precision floor（0.4333）** → **单独看那一行会被读成失败。**

### 5.13 统计：为什么不能只报一个数字

**做法**：同一批 252 行，**逐题比较**两个模型（配对），用 bootstrap + 精确 McNemar 检验。

**🔑 一个"正对照"（预先注册的判据）**：

```json
{"pair": "BASE_zero_shot vs SFT", "accuracy_delta": 0.40873,
 "p_exact_two_sided": 2.83196e-26,
 "requirement": "p <= 0.001 or the script exits", "passed": true}
```

**为什么需要它**：它是用来**证明统计工具本身是灵的** —— 如果连这么大、这么明显的差异都测不出来，脚本**直接退出、不输出任何结论**。

**⚠️ 一个必须说明的适用边界（新发现）**：这份配对检验**只做了"分类准确率"这一项**（`macro-F1` 因为不能逐行分解，只作边缘估计）。
**另外四张卷子为什么不做同样的检验，项目没有写理由** → 所以
**"RL 没赢过 SFT"这句话的适用范围，就是"分类准确率这一张卷子"。**

**⚠️ 还有一处矛盾的措辞（新发现，待核对）**：同一份文件的同一个块里，相邻两行写着

- *"the lr effect is not detected at every group size measured, **so group size is not excluded as the cause**"*
- *"**this removes group size as the cause** of the lr effect."*

**一句说"组大小没有被排除"，下一句说"这排除了组大小"。** 引用时必须先决定采信哪一句。

## 6. 强化学习后训练（第四阶段）

> **入口命令**：`bash scripts/24_train_grpo.sh`（或走队列脚本 `29_grpo_train.sh`）
> **起点**：**从 SFT 适配器继续训练**（不是从基础模型重来）

### 6.1 为什么 SFT 之后还要再走一步

| | SFT（第二/三阶段） | RL（本阶段） |
|---|---|---|
| 怎么学 | **抄答案**（有标准答案，照着背） | **自己答题，按得分调整** |
| 信号 | "这句话应该这么说" | "这次得了 1.8 分，比平均好，往这个方向走" |
| 像什么 | 背课文 | 刷题 + 对答案 |
| 局限 | 只会**模仿课本**，包括课本里错的地方也照抄 | 想让它**追求"得高分"**而不是"背得像" |

### 6.2 打分器：四个**确定性规则**（没有任何模型或人参与）

| 奖励函数 | 权重 | 判什么 |
|---|---|---|
| `WaferClass` | **1.0** | 报告的缺陷类别是否等于可信标签 |
| `WaferRadial` | **0.4** | `radial_zone` 是否等于确定性几何算出的值 |
| `WaferClock` | **0.4** | 钟点方向是否在几何金标的 **1 格以内**（环形距离） |
| `WaferFormat` | **0.2** | 回复是不是一个 JSON 对象、且七个字段齐全（按字段比例给 0~1） |

**满分 = 1.0 + 0.2 + 0.4 + 0.4 = 2.0。**

**插件文件开头写明了为什么不用大模型当评委**（原文）：

> *"Nothing here calls a model, an API or a judge: an LLM judge used as the reward would let the policy drift toward whatever the judge happens to like, and the gold label and the circle-fit geometry are the only two sources this project treats as trustworthy."*
>
> **翻译**：用大模型当评委，模型会往"评委碰巧喜欢的样子"漂，而不是往"答对"漂。

**一个很讲究的设计**：当某个字段**没有金标时，奖励返回常量 1.0**（而不是 0）。
代码注释原文：*"an unscoreable field contributes no advantage rather than a free point that would reward guessing"*
**翻译**：**"没法评分"传达 0.0 是错的信息**（会让模型以为"答错了"）；而给常量 1.0 则**不产生任何优势**（因为组内所有答案都一样）—— 这样"不可评分"既不奖励、也不惩罚。

**另外还有一层容错**：如果模型把答案包在 ` ```json ... ``` ` 里，**照样算它答对了** —— 因为"给了可用答案却判成格式失败"会把正确行为训练掉。

### 6.3 GRPO 的机制（三条）

#### 6.3.1 组内比较（"组"的来历）

**老办法的难处**：早先的方法（PPO）需要一个**额外的小模型**（critic）来预测"这个题大概能得几分"，才知道自己答得比预期好还是差 —— 而这个小模型**也得训、也占显存、还可能不准**。

**GRPO 的省法**：

> **不预测"应该得几分"，改成"和同组的其他答案比"。**

所以让**同一张图答 G 次**（本项目 G = 4/8/32），这 G 个答案天然构成一个参照系。

#### 6.3.2 优势

$$\text{优势} = \frac{\text{你的分} - \text{组内平均分}}{\text{组内标准差}}$$

- **分子**：你比同组平均好多少
- **分母**：把差距缩放到差不多的尺度 → **与"绝对分数"无关**（打分器只需要排出高低，不需要打得准）

**举例**：

| 情形 | 组内 4 个答案的分 | 会发生什么 |
|---|---|---|
| **全是满分** | 2.0 / 2.0 / 2.0 / 2.0 | 都等于平均 → **优势全 0 → 白跑一步** |
| 有差别 | 2.0 / 1.8 / 1.6 / 1.4 | 2.0 被鼓励（+1.34）、1.4 被打压（−1.34） |

**第一种就是"零优势步"** —— 项目第一次训练的第一步就是它：

```
first_step:  reward 2.0 · reward_std 0.0 · frac_reward_zero_std 1.0   ← 100% 白跑
```

**为什么全满分反而白跑**：因为 GRPO **只看组内高下，不看绝对分数**。四个都是满分 → 没有高下 → 不知道往哪调。

#### 6.3.3 KL 惩罚（一根缰绳）

每更新一步，都算一次"现在的模型离 SFT 模型偏了多远"，**偏得越远扣得越多**。
**目的**：防止模型为了拿分**把话说乱**（反正打分器只看类别对不对）。
**本项目取值**：`beta = 0.04`；KL 从第 1 步的 **1.329** 降到最后的 **0.8077**，全程平均 **1.107**。

### 6.4 GRPO 与 GSPO 的区别（**同一个参数换一个值**，不是换算法）

ms-swift 里的 `rlhf_type` 枚举**不含 `gspo`** —— 但据此断言"GSPO 无法执行"是**错的**：

> **GSPO 不是独立的算法名，而是 GRPO 的损失变体，由 `--importance_sampling_level sequence` 开启**（默认值 `token` 就是普通 GRPO）。

**这个教训很值得记**：*"只查了一个枚举名就断言某个算法不存在，而真正的开关是同文件里的另一个参数"* —— 因此**第一次跑的其实是普通 GRPO，不是 GSPO**，后来按论文补跑。

**两者的差别**：归一化算在哪个层级 —— GRPO 是每个 token 各算，GSPO 是整句算一个。

### 6.5 实验网格：10 个 run

**三个轴**：算法（token/sequence）× 组大小（4/8/32）× 学习率（1e-5/5e-5）。

| 算法（归一化层级） | 组大小 | **实际有效批次** | 学习率 1e-5 | 学习率 5e-5 |
|---|---|---|---|---|
| token（GRPO） | G = 4 | 16 | ✅（含 3 个种子） | ✅ |
| sequence（GSPO） | G = 4 | 16 | ✅ | ✅ |
| sequence（GSPO） | G = 8 | 64 | ✅ | ✅ |
| sequence（GSPO） | G = 32 | **1024** | ✅ | ✅ |

**共 10 个 RL run**：GRPO(token) G=4 lr1e-5 **三个种子**（3407/3408/3409）+ G=4 lr5e-5；GSPO(sequence) 在 G=4/8/32 × lr1e-5/5e-5 **六个**。

**每个 run**：150 步；都从 SFT 适配器出发；都在同一张考卷（同样的 1512 条请求）上评估；都用同一批奖励函数与权重。

**⚠️ 这不是完整的 2×3×2 = 12 格** —— **缺的格子正是下面两个混淆的根源。**

### 6.6 ⚠️ 两个混淆（这一节是全篇实验设计的关键）

**"混淆"（confound）**：一次改动**同时动了两个变量** → 无法判断是哪个造成的。

#### 6.6.1 混淆一：算法与组大小**绑死**

最早的设计是：

```
token 级（GRPO）   →  只在 G=4
sequence 级（GSPO）→  只在 G=8 / G=32
```

**所以那时的"GRPO vs GSPO"对比，同时改了算法和组大小两样东西** → 分不开是哪个造成的。

**这个混淆后来被部分解开了**：项目**补跑了 sequence 在 G=4 的两个学习率**，于是第一次有了这么一对：

```
GRPO(G=4) lr5e-5   vs   GSPO(G=4) lr5e-5
组大小 4 = 4 · 有效批次 16 = 16 · 学习率一样 · 种子一样 · 同步数 · 同数据 · 同奖励函数与权重
只差一个参数：--importance_sampling_level
```

**这被称为"本项目的第一个真正单变量对照"。结果**：准确率差 **−3.17 个百分点**，95% CI [−7.94, +1.59]，**p = 0.268 → 分不开**。

#### 6.6.2 混淆二：**有效批次 = 组大小²**（这个最严重）

**先解释名词**：

- **微批次**：一次送进显卡几张图
- **梯度累积**：攒几次再更新一次模型（显存不够时的常用手法）
- **有效批次** = 微批次 × 梯度累积 = **一次参数更新实际看了多少个样本**

**项目踩的坑**：训练时**把梯度累积设成了与组大小相等**（4/4、8/8、32/32），而微批次一直是 1：

| 组大小 | 真实累积步 | **有效批次** |
|---|---|---|
| G=4 | 4 | **16** |
| G=8 | 8 | **64** |
| G=32 | 32 | **1024** |

**后果**：

> **「把组大小从 8 加到 32」这一次改动，其实是"组大小变 4 倍"和"有效批次变 16 倍"同时发生。**
> **所以结论只能读成"加组大小**或**加有效批次无效"，不能归给组大小。**

**⚠️ 顺带暴露出一个"记录在说谎"的实例**：训练记录里的 `grad_accum` 字段是**写死的常量 4**、不读任何环境变量
→ 所以 **G=8 和 G=32 的记录都写 4，实际跑的是 8 和 32**（三处不符）。

**怎么发现的**：去 `/proc/<进程号>/cmdline` 读**正在运行的那个任务的真实命令行**，看到 `--gradient_accumulation_steps 32`，而记录写 4。
**为什么不当场改**：那个脚本**正在被执行**，改运行中的 `.sh` 会移动 bash 的续读位置 —— **项目已经因此丢过两个 run**。所以**记录在案、等跑完再改**。

### 6.7 那还剩什么能比？—— **学习率那一列**

**为什么它干净**：在**每个固定组大小内部**，两个学习率都跑了 → **组大小固定 → 累积固定 → 有效批次固定**。两个 run 之间**只差学习率**。

**读数**（同一批 252 行做配对比较）：

| 对照 | 准确率变化 | 95% CI | p | 结论 |
|---|---|---|---|---|
| GRPO G=4：1e-5 → 5e-5 | **−5.56 个百分点** | [−9.92, −1.19] | **0.0243** | **显著下降** |
| GSPO G=4：1e-5 → 5e-5 | **−9.13 个百分点** | [−13.49, −5.16] | **3.4e-05** | **显著下降** |
| GSPO G=8：1e-5 → 5e-5 | **−7.54 个百分点** | [−11.90, −3.17] | **0.00132** | **显著下降** |
| GSPO G=32：1e-5 → 5e-5 | −5.16 个百分点 | [−10.71, +0.40] | 0.0984 | 不显著 |

**两个算法都掉 → 掉分是【学习率】的事，不是算法的事。**（严格说：在 G=4 与 G=8 上这样；G=32 那一格没测出显著。）

**这一条是全篇唯一有"跨算法印证"的结论。**

### 6.8 论文的中心主张：**未被证实，也未被否定**

论文主张：*"序列级归一化比 token 级更能容忍更高的学习率"*。

**检验它需要的**：一对**只差归一化层级**的配置 —— 项目**真的跑出来了**（就是 §6.6.1 那一对）。

**结果**：准确率差 −3.17 个百分点，p = 0.268 → **分不开**。

**但机制层面测得出差别**（见 §6.10）。

**⚠️ 而且这一对只覆盖了 lr 5e-5 一个学习率**，而"更耐高学习率"是关于**学习率效应大小**的比较
→ 所以论文主张**仍然未被完整检验**，只是它的一个必要部分第一次有了无混淆的读数。

### 6.9 组大小呢？—— 也没测出东西，而且**不能单独归因**

**三点序列**（同为 GSPO、sequence、lr 5e-5，让组大小从 4 走到 8 再到 32）：

| 档 | 准确率变化 | p |
|---|---|---|
| G=4 → G=8 | +0.40 个百分点 | 1.0（分不开） |
| G=8 → G=32 | +2.78 个百分点 | 0.410（分不开） |

**沿这条序列，准确率对组大小是"平的"。**
**但这条序列不是单变量**：组大小走了 8 倍、有效批次走了 64 倍 —— 所以它是一条**配置空间里的路径**，不是受控实验。

**论文原始设定的那一格**（GSPO G=32 vs GRPO G=4，同为 lr 5e-5）：准确率**完全相同**（+0.0000，p = 1）。
**但这不代表"逐行相同"**：两者在 252 行里有 **64 行判断不同**，恰好 32 对 32 互补 —— **聚合值相等是互相抵消的结果**。

### 6.10 机制层面**确实看得见**差别（但没转成分数）

在唯一"只改一个参数"的那一对（GRPO(G=4) lr5e-5 vs GSPO(G=4) lr5e-5）上：

| | GRPO | GSPO |
|---|---|---|
| **零优势步占比** | **32.67%**（49/150） | **26.67%**（40/150） |
| 准确率 | — | 差 −3.17 个百分点，p = 0.268（分不开） |

> **机制层面的差异测得出（低 6 个百分点），基准分数上的差异测不出。**

**另一组观察（不能归因）**：lr 1e-5 下 GSPO(G=8) 的零优势步是 15.33%、GRPO(G=4) 是 36.00% ——
**但这一对同时改了组大小**（8 对 4），所以只能算**观察，不是归因**。

**四个奖励各自的"信号强度"**（跨步的组内标准差，越大越能分出高下）：

| 奖励 | 平均组内标准差 | 读法 |
|---|---|---|
| `WaferClock` | **0.2244** | 最能分出高下 |
| `WaferRadial` | 0.1180 | 次之 |
| `WaferClass` | 0.0803 | 权重最大，但**波动小**（大多答对，全是 1.0） |
| `WaferFormat` | **0.0005** | **几乎不产生优势**（格式早就学会了 → 永远满分 → 没有差别） |

### 6.11 判定：**保留 SFT，不宣称 RL 有效**

**项目预先定的判据**（引自论文 §8.11）：*"若提升落在置信区间内，结论写『未观察到显著提升』，不写『RL 有效』"*，并给出分支 *"保留 SFT 为最终模型"*。

**实际结果**：

| RL run | 准确率 | 与 SFT 之差 | 配对检验 |
|---|---|---|---|
| **GRPO G=4 lr1e-5** | 0.6230 | **±0.0000** | p = 1.0（与 SFT 无法区分） |
| **GSPO G=4 lr1e-5** | 0.6270 | **+0.40 个百分点** | p = 1.0（无法区分） |
| GSPO G=8 lr1e-5 | 0.6151 | −0.79 个百分点 | p = 0.815（无法区分） |
| GSPO G=32 lr1e-5 | 0.6190 | −0.40 个百分点 | p = 1.0（无法区分） |
| GRPO G=4 lr5e-5 | 0.5675 | **−5.56 个百分点** | **p = 0.0436 → 显著下降** |
| GSPO G=4 lr5e-5 | 0.5357 | **−8.73 个百分点** | **p = 0.00031 → 显著下降** |
| GSPO G=8 lr5e-5 | 0.5397 | **−8.33 个百分点** | **p = 0.00032 → 显著下降** |
| GSPO G=32 lr5e-5 | 0.5675 | −5.56 个百分点 | p = 0.0869（无法区分） |

> **没有一个 RL run 显著超过 SFT；最好的一个只多答对 1 道题（158 对 157）。**
> **而学习率调到 5e-5 的那批显著退化（少答对 14~22 道题）。**

**最终模型 = SFT 检出点（`qwen35_9b_qlora_v1`）。**

**⚠️ 必须说清的适用范围**：

- **这"不等于"「GSPO 不如 SFT」** —— 在 lr 1e-5 上三者两两都落在噪声内；在 lr 5e-5 上**两个算法都显著低于 SFT**（所以**算法不是差异的来源**）
- **判定用的是"分类准确率"这一张卷子** —— 另外四张卷子 RL 也有成绩（见 §5.7 主表），但**没有做同等强度的检验**，且"为什么不做"项目没有写理由
- **RL 的模型在五张卷子上都有分**：例如 `GSPO_G4_lr1e5` 分类 0.6270 · 结构化类别 0.5794 · 描述要点命中 0.7381 · 鲁棒性 0.5807 · 检索 0.3748
- **检索那一列是个例外**：有几个 RL run 高于 SFT（最高 `mAP@10 = 0.4337`）—— 但那一列本身另有问题（见 §5.11.5）

### 7.4 从这 45 条里能提炼出的四条"可复用规律"

1. **检查坏了比不检查更危险**：一个从没运行过的检查（A08）、一个喂自己造的数据的检查（B06），都会给人"已经验过了"的错觉。
   项目的原话：*"一个拦不住被检查对象的检查，就是一行日志。"*
2. **标记在说谎比检查坏更严重**：检查坏了最多是没拦住；**标记坏了会让下游把"没做"当成"做过"**（`grad_accum` 写死 A11、完成标记被写反 A08）。
3. **"同源"会让错误自洽**：当训练答案与评测标准是同一个数字时（B01），错误不会报警 —— 只能靠外部事实（真值标签、视觉直觉）发现。
4. **缺席也要记录**：没做的步骤（教师盲测 B10、视觉侧评估 B03、换判据复核的 RL 部分 B19）如果**不被记进清单**，后来的人会以为它做了。
   **"没测过"不等于"等于 0"，也"不等于"不存在。**

## 10. 复现步骤（关键命令）

> 完整命令与哈希记录在 `scripts/*.sh` 与 `provenance.json`。以下为主干步骤。

```bash
# 环境
bash scripts/00_doctor.sh                  # 环境自检
bash scripts/01_download_model.sh          # 下载并校验 Qwen3.5-9B（4 个分片）

# 数据

python -m wafer_vlm.cli benchmark build    # 构建 wafer_bench_v1（252 核心 + 检索关系表）

# 训练与评测
bash scripts/10_train_qlora.sh             # QLoRA SFT（604 步，约 2 小时 11 分）
bash scripts/20_run_benchmark.sh           # 零样本基线
bash scripts/22_eval_adapter.sh            # SFT 适配器评测
bash scripts/23_merge_and_check.sh         # 合并 + 等价性校验
bash scripts/25_finalize.sh                # 评测、检索、对比、报告汇总

# 强化学习
SMOKE=1 bash scripts/24_train_grpo.sh      # 先跑 2 步冒烟（82 秒）
bash scripts/29_grpo_train.sh              # 正式 RL（本报告为 150 步）
bash scripts/30_eval_grpo.sh               # RL 评测（同一个 all_requests.jsonl）
```

**复现时的三个已知陷阱**：

1. **写脚本 ≠ 跑脚本**：基线脚本里写的样本数是 756，**实际跑的是 1512**（B15）。判断"实际用了什么参数"，**优先看日志与产物，其次才看脚本**。
2. **运行中的 `.sh` 不要编辑**：会移动 bash 的续读偏移（项目已因此丢过两个 run）。
3. **venv 与 ms-swift 源码是软链**（指向实例盘）：只搬项目目录会失效。

## 12. 一页纸总结

**做了什么**：把 WM811K 的 5904 张晶圆 BIN 图标准化（448×448 无损 PNG + 21 个几何特征），按批次切分（杜绝同批次泄漏），用两个大模型教师给训练集写描述与结构化答案（5,315 张 → 接受 4,829 / 隔离 486），产出 12,876 条训练样本；用 QLoRA（4bit + LoRA rank16）在单张 RTX 4090 上微调 Qwen3.5-9B 两小时十一分；用五张冻结的卷子考试；再跑 10 个 RL 实验（GRPO/GSPO × 组大小 4/8/32 × 学习率 1e-5/5e-5）。

**结果**：分类 **0.2143 → 0.6230**（配对检验 p ≈ 2.8e-26），**根因幻觉率 0.2183 → 0.0000**，鲁棒性 0.1905 → 0.5622，检索 mAP@10 0.3236 → 0.3873；**强化学习没有一个 run 显著超过 SFT**（最好的多答对 1 道题），**学习率加 5 倍反而显著更差**，因此**保留 SFT 为最终模型**。

**三个最诚实的地方**：① 基准的**人工双审未完成**，所有分数都是草稿分；② 有一个字段（`radial_zone`）**因为标签口径缺陷而作废**，我们查出了原因并换了三种判据重打分；③ 强化学习我们**主动报告了"没赢"**，而不是拿它当成果。

**三件最需要你拍板的事**：① **主教师选型与是否重标**（§8.1 问题 1、2）；② **人工双审的人力安排**（§8.3 问题 14）；③ **下一步优先级**——我们的建议是"**先修标签、再谈换模型**"（§8.4 问题 19）。
