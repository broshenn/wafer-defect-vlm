### 1.1 B49 —— 检查器那两条真是缺陷 **[事实，已复现]**

**缺陷一**：`verify_glm_preparation.py:159` 从 `allb`（**180 个全是 train 的样本**）取
val/test 的 lot → 两个集合**恒为空** → 后面的交集检查**恒真**。

**缺陷二**：`:173` 的 `bm_lots = {man[i]["lot_name"] for i in bm_ids if i in man}` ——
`if i in man` **静默吞掉未知 ID**。实测 benchmark 有 **1008 个 ID，其中 756 个带派生后缀**
（`__recolor_v1` / `__resize_224` / `__rotate_90_ccw`），它们**不在 manifest 里**，
被这句话默默丢掉，去重后只剩 252 个根晶圆参与检查。

**修正后实测**：

| 项 | v1 | **v2** |
|---|---|---|
| val lot | **空集**（检查无效） | **372 个**（非空） |
| test lot | **空集** | **385 个** |
| benchmark | 静默丢 756 个派生 ID | 映射回 **252 个根晶圆 / 202 个 lot**，未知根 ID **显式失败** |

**结论**：**是的，v1 那两条检查当时证明不了外部划分隔离。**
但如 B49 所述 —— **这不是"数据实际泄漏"**。v2 用完整 manifest 重跑，
**五组交集实测仍全 0**。

### 3.1 准备器 v2 改的两处 **[事实，已实测]**

1. **`task_book` 指向实际文件**：v1 写 `任务书_20261002_ClaudeCode_GLM标注准备.md`，
   **那个文件不存在**；实际是 `任务书_20261002_ClaudeCode_GLM训练标注准备.md`（多了「训练」二字）。
2. **`--resume` 复用已有 `prepared_at`**：v1 每次刷新时间戳 → `plan.json` 的 hash 每次都变，
   而 hash 是验收依据，等于没有稳定产物。

```
第 1 次 --write        退出码 0

第 3 次 --write --resume  退出码 0
→ plan.json / zcode_batch_01_inputs.json / batch_01_blind.jsonl
  三个文件在 resume 前后**逐字节相同**
```

**并且 `batch_01_blind.jsonl` 的 hash 与已冻结的那份完全一致**（`0c2f476d…`）——
**修复只动了元数据处理，没动数据。**

### 3.2 无重名 schema 只改该改的 **[事实]**

`batch_log_no_dupkey.json` 与原件做**全叶子字段对比**（86 → 87 个）：


`failure_details`（详情）。**没有重复的 `not_executed` 保持原名不动** ——
