多模态模型微调与评测口径建设　|　Qwen3.5-9B · LoRA SFT · 冻结枚举评测 · 同基座对照
  • 背景与目标：晶圆 BIN 图（格状缺陷热力图）判读核心是「格局属哪一类」，质检沟通还需一句中文描述。目标：把「类别能力」与「描述能力」分开建模评测，回答「该不该给描述监督」。
  • 参与动作：基于公开数据集 WM811K 的 5904 张抽样子集（固定种子 3407；train/val/test = 4721/594/589，跨划分 lot 交集为 0），按类别分层抽 3072 张训练池；在同一基座 Qwen3.5-9B 上 LoRA 微调两个同输入、同题面、只改监督答案的模型：L 只监督类别标签，D 监督类别 + 形态 + 中文描述。
  • 评测口径（关键工作）：把「描述是否与图相符」的评法从自由文本正则改为冻结枚举 schema：六维枚举（SUPPORTED / PARTIAL / CONTRADICTED / UNCERTAIN / MISSING / NEEDS_REVIEW），并把「方向」拆成 applicable 与 verdict 两列；改口径后先跑 20/20 回归才开工。
  • 对照设计：固定 36 图开发集，同题对照 8 个模型 —— 本项目 L/D、原生基座、四个商用 API 模型与外部 GLM；冻结题面 sha256、固定解码参数，日志留痕可复算。
  • 留出候选补测：另用 56 张与训练池 ID / lot / PNG 内容交集均为 0 的图，在同基座、同题面、同解码参数下补测 Base / L / D，并做同图配对差与 10000 次按图 bootstrap（seed 3407）；复核时把「视觉四维」与「格式」分列，不合成单一描述准确率。
  • 实测结果（56 张留出候选：与训练池的 ID / lot / PNG 内容交集均为 0）：同基座只把监督从「无」换成类别标签，准确率 0.2679 → 0.8214（同图配对 bootstrap 区间 [0.411, 0.696]，不含 0）；描述监督的 D 为 0.7679，与 L 之差 [−0.054, +0.161] 跨 0（类别字段独立口径 [−0.018, +0.179] 同样跨 0）—— 本轮分不出高下。开发集 36 图上同基座对照 0.1667 → 0.8889，84 张开发验证集 77/84（91.7%）。基座原生输出带 Markdown 围栏，严格 JSON 判分几乎全失败：必须把「格式失败」与「内容错误」分开计。
  • 负结果（同批同图实测）：（1）加了描述监督，类别准确率反而下降（0.8889 → 0.6944）；（2）本项目的描述并不优于外部零样本大模型 —— 视觉四维「好/坏」为 qwen3.8-max 113/3、GLM 105/10，优于 L 89/12、D 85/19；（3）L 六维合计垫底完全由「格式」一维造成，去掉格式后其视觉四维反好于 D，准确说法是「视觉内容中上、格式合规最差」；56 图留出候选上这一现象复现（L 视觉四维最差项最少 12/224、格式却坏 51/56，仍是把 JSON null 写成字符串 "null"）；（4）格式违规会压低类别分：L 唯一一条 schema 不合法里类别其实答对（Scratch，真值也是它），被 radial_zone 越界拖成「全 schema 门控未接收」——原门控 46/56 = 0.8214、类别字段独立口径 47/56 = 0.8393；三模型严格 JSON 均 56/56 可解析，不是解析失败；（5）56 张里记录到 4 张「AI 判读与公开标签疑似分歧」（例：标 Center 的图除最外圈外几乎全红）——这是分歧记录，未证实原标签错误，标签一个没改，也不据此宣称历史成绩被标签噪声压着天花板。
  • 个人边界：数据全部来自公开数据集，未使用公司内部数据、未做产线部署；描述结论是模型自查，不是人工金标；36 图是开发集，56 图是可见历史隔离后的留出候选（七类、缺 Near_full / none，完整历史接触未核，仍不是独立九类盲测卷）；36 图 ID/lot 与训练池交集为 0，但其中 1 张与训练图 PNG 逐字节同内容，故不得称「图像内容从未见过」（剔除后 35 图：L 88.6%、D 68.6%）；本项目模型见过领域标签、外部模型为零样本，分数差不是训练预算对齐的因果对比。
推理服务化与可审计交付　|　HTTP 服务 · Schema 校验 · 审计留痕 · 性能实测 · 预算守卫
  • 背景与目标：工业质检里模型输出的可审计性与准确率同等重要：需知道结果是模型原样给的还是服务改过的，也需「不确定、请人工看」标记。
  • 参与动作：把微调模型落成真实 HTTP 推理服务，设三条硬约束：输入合法性校验、JSON schema 校验、原答逐字节保留。关键取舍为 schema 不合不修补：坏结构一律标 needs_review 并留原答，只把「服务改过什么」单列成 format_changes 审计项。
  • 工程化：对照侧设 20 元硬预算守卫（在途按 max_tokens 预留、完成按实际 usage 结算），并写死「每图一次请求、客户端重试 0、失败原件保留、不重新调用」，避免重试带来的选择偏差。
  • 实测结果：租用单卡顺序完成 Base / L / D × 56 图 = 168 条真实推理，0 失败，单卡占用 541 秒（9.02 设备分钟），峰值显存约 19.1 GiB，释放后 1 MiB、无残留进程；每条先写 started 台账、再存原答与四项哈希（图片 / 题面 / 检查器 / adapter）。固定 36 图真实 HTTP 回放 —— 36/36 返回 200，类别判对 25/36（固定 9 类 Macro-F1 0.6756），needs_review 19 条；时延 p50 ≈ 4.2 s、p95 ≈ 4.9–5.4 s；峰值显存 17.88 GiB；CPU 工程契约测试 6/6 通过。API 对照 4 模型 × 36 图共 144 次尝试（132 正常返回 + 12 连接层失败），按标准价用量估算约 4.90 元 / 20 元上限（不是平台实付，失败未重发）。
  • 不达标项（照实写）：「HTTP 通过」≠「内容正确」：36/36 返回 200 但仅 25/36 判对；时延是同客户端端到端，不是外部网络时延；12 条为连接层失败（非模型答错），为遵守「不做二次调用」纪律未补齐。
  • 个人边界：服务只跑在已获准的租用实例上做真实回放，未公网发布、未产线试点，故无 QPS 与线上稳定性数据；GPU 计费分钟与租机人民币实耗仓库内无账单可核，不代填。
