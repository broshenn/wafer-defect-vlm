## 一、现在挂在哪、怎么判、怎么抢

| 机器 | 进程 | 判据 | 动作 |
|---|---|---|---|
| **5090** | 3 个 `queue_existence.sh`（Base / L-N3072-3407 / D-N3072-3407） | 任意一张卡**完全没有进程**（`n == 0`） | `mkdir` 原子锁认领 → 立刻跑 D 段 |
| **A100** | 3 个 `A100_监视与抢卡.sh`（同上三模型） | **先等驱动恢复**，再等任意一张卡 `n == 0` | 同上 |

**两边的进程都用 `setsid nohup` 起，会话断了也继续跑。**

### 「先占了」是怎么实现的 —— **没有占位进程**

红线是**不建占位进程**。这里的做法是：**进程一直停在队列里，不碰 GPU**，
每 30 秒查一次；一旦某张卡空了，`mkdir` 抢到锁（防三个队列抢同一张卡），
**立刻启动真实任务**。

所以「先占」占的是**启动时机**，不是**显存**。全程没有任何进程在空转占卡。

## 二、5090：判据为什么这么写（**上一轮的教训固化成注释**）

`chain_one.sh` 里那句 `|| [ "$o" = "<本人账号>" ]`（「卡上只有我自己的进程也算空闲」）
是 2026-10-08 凌晨**三条链同时 OOM** 的直接原因。
新脚本里：

- 判据**只认 `n == 0`**，并且在注释里**显式点名那句旧判据**，防止以后被抄回去；
- 加了一道**显式前置检查**：先确认 `nvidia-smi` 本身跑成功。
  因为它失败时输出为空，`grep -c` 会得 0 —— **看起来像「卡是空的」**，
  这会直接导致 OOM。现在失败就跳过该卡；
- 再查一次 UUID，**故障卡跳过**（2026-10-08 遇到过 GPU0 `ERR!`/ECC 状态
  导致 `CUDA_VISIBLE_DEVICES` 变无效）。

## 三、A100：这台机器**驱动整体卡死**，检测本身不能帮倒忙

### 现状（证据）

| 现象 | 证据 |
|---|---|
| 全机 **52 个 D 状态进程**（不可中断睡眠） | `ps` 直接数出来 |
| 绝大多数是 **`gq` 的 python，卡了一个多小时** | 最久的 `01:20:04` |
| 一个 **root 的 `nvidia-container`** 卡 42 分钟 | |
| **别的用户 `lzj` 的 `nvidia-smi` 也卡住** | 不是只有我们 |
| **`kill -9` 杀不掉** | 8 个 nvidia-smi 一个没少 |
| **直接 torch 分配显存也卡住** | `timeout 30` 拉不回来 |

**没有任何人在用 GPU**（扫 `/proc` 的 nvidia 句柄确认过）—— 它们不是「忙」，是**冻住了**。

### 所以恢复判据按**风险从低到高**排

1. **重启检测**（**完全不碰 GPU**）：`/proc/uptime` 变小 = 机器重启过 → 驱动必然是新的；
2. **D 进程清空**：nvidia 相关 D 进程降到 ≤1 → 很可能已恢复；
3. 满足 1 **或** 2 之后，才做**一次**真实探测（`timeout 25 nvidia-smi -L`）。
   **若这次反而挂住，它会自己变成 D 进程** —— 所以之后**至少歇 40 分钟**不再探测。

这样最坏情况下也就是一小时多两个卡死进程（重启即清），
不会像盲目轮询那样把 D 进程堆成一片。
