## §1 训练门槛必须真能停止

**原问题**（Codex 指出，确认成立）：`train_desc.py` 的 `DescGate._ck()` 只打印并返回 False，
整个回调类**没有 raise**。冻结、设备、更新或梯度任一检查失败，训练照跑，
不符合合同「失败即停」。

**改法**（`train_desc_v2.py`）：

| 项 | v1 | v2 |
|---|---|---|
| 检查失败 | 只打印 FAIL | 记录后**抛 `GateFailure`**，并把 `gate_report.json` 落盘 |
| 触发时机 | `on_step_end`（预设该步日志已在） | **`on_log`**，此时第 2 步日志已入 `state.log_history`、优化器也已 step 两次 |
| 空列表风险 | 可能取 `ls[0]` | 先判 `len(losses) >= 2` 才进门槛 |
| 「loss 下降」 | 当作判据 | **移出硬门槛**——两个不同小批次的 loss 本就无需单调 |
| 更新判定 | 只看 `lora_A` | **快照含 `lora_B`**，硬判定用 B；`lora_A` 另行如实记录 |
| 收敛判断 | 两步比较 | **全程记录 loss 趋势，不用两步判断收敛** |
| 结束断言 | 无 | 训练后断言门槛**确实执行过且通过**，否则返回 5，本轮不成立 |

**`lora_B` 那一条是对的，我确认了机理**：LoRA 的 B 是零初始化，
第 1 步 `dL/dA = (dL/dout)·B·x = 0`，所以只看 `lora_A` 会误报「未更新」。

**v2 的硬门槛**：视觉侧完全冻结 · 全部可训练张量都是 LoRA · `device_count==1` ·
已取得第 2 步 loss 日志 · loss 全部有限 · `lora_B` 确有更新 · 记录到 2 次优化器 step 的梯度 ·
存在非零 LoRA 梯度 · 梯度只落在 LoRA 上 · 视觉模块确被调用 · 模型参数只在单卡。

> **状态**：脚本已改，**未在 GPU 上跑过**（无卡）。门槛逻辑本身无法在 CPU 上端到端验证，
> 只做了静态核对。**not run。**

## §2 补核 collator 之后的监督证据

**原问题**（确认成立）：v1 调了 collator，但逐条解码用的是 `enc[i]['labels']`（encode 结果），
`batch['labels']` 只检查存在与形状；而「问题全 -100」又以第一个非 -100 位置定义边界，
**不能独立证明没有问题被监督**。

**改法**（`desc_gate_data_v2.sh` 的 C 段）：改用 **batch 张量** `input_ids / labels / attention_mask`，
按 padding 对齐后检查：

| 检查 | 结果 |
|---|---|
| 三个张量形状一致 | ✅ `(20, 604)` |
| padding 位置全 -100 | ✅ 异常 0 |
| 非 -100 的 labels 等于同位置 input_ids | ✅ 异常 0 |
| 视觉 token 位置全 -100 | ✅ 异常 0 |
| **监督内容精确等于 assistant 目标** | ✅ 异常 0 |

**门槛结果：18/18 通过。**

**过程中查出一个我 v1 没发现的事实**：监督段末尾是
`…"}<|im_end|>\n`——**结束标记之后还有一个换行 token**。
所以不能按「最后一个 token 是 eos」剥离（那样 `<|im_end|>` 会留在文本里，
长度差 11 个字）。必须按模板结束标记的**文本**剥离。这一版已按此实现，
并额外断言剥离后不再残留任何 `<|…|>` 特殊标记。

三种任务各留了一条实际 batch 解码作为证据（见 `门槛_数据_v2.json` 的 `三种任务实际解码`）：

```
[结构化_含不确定] 剥离前尾部: '居中但略微偏离几何圆心"}<|im_end|>\n'
[结构化_无不确定] 剥离前尾部: '布少量绿色合格die。"}<|im_end|>\n'
[类别Caption辅助]  剥离前尾部: '红簇，其他区域零星红点"}<|im_end|>\n'
```

## §3 JSON 可解析 与 七字段合法 必须分别计数

**原问题**（确认成立，Codex 已离线复现）：v1 的 `parse7` 只判「是不是合法 JSON 对象」，
于是 `{}`、仅 `defect_class` 的对象、七字段全为非法类型的对象**都返回 `how='ok'`**，
并被 `summarise` 计进「七字段合法率」——**通过率会是 1.0**。这是错的。

**改法**（`eval_desc_v2.py`）：

- `parse_json()` 只判 JSON 可解析，产出 **JSON可解析率**；
- 新增 `schema7()` 判七字段合法性，产出 **七字段合法率**；
- **两个数分开命名、分开报告，不可互相替代或混名**；
- schema 判据：七键集合齐全且无多余键 · `defect_class` 为九类或 `unknown` 的字符串 ·
  `radial_zone` 为六值枚举字符串 · `clock_direction` 为 string 或 null ·
  **`extent_r` 必须是真 JSON null（字符串 `"null"` 不算）** ·
  `morphology`/`caption_zh`/`uncertainty` 为 string · **空 Caption 另计**；
- 分类辅助从**可解析且类别枚举有效**的 JSON 抽取，**明确不要求七字段齐全**，
  与上面两个通过率分开命名；
- **每条推理完成即写 JSONL 并 flush**，保留原答、解析结果、schema 结果、`finish_reason`；
  中断时已完成答案不丢；
- 生成上限仍 256，不重试、不扩额。

**离线回归**（`回归_解析与schema.py`，**未发任何模型请求**）：**19/19 通过**，
覆盖 Codex 点名的空对象、单字段、重复键、坏类型、合法完整对象，
另补 `extent_r:"null"` 字符串、`defect_class` 为 bool、`radial_zone` 为 null/越界、
`clock_direction` 为数字、多字段、截断、尾随文本、两个对象、散文、`</think>` 残留。

其中 **10 条属于「可解析但七字段不合法」**——正是 v1 会错误计入合法率的那一类：

```
空对象 · 仅 defect_class · extent_r 是字符串 null · defect_class 是 bool ·
defect_class 越界 · radial_zone 为 null · radial_zone 越界 ·
clock_direction 是数字 · morphology 是数字 · 多字段
```

> 回归里我第一版用例自己写错了（`GOOD.split("\n\n",1)[1]` 取到的是带 `</think>` 的串），
> 解析器正确拒绝了它，是用例的问题不是解析器的问题，已修用例并补了一条「仅有 `</think>` 残留」。
