## 五、过程中的问题（全部是我的，如实记录）

### 5.1 两次失败尝试，共 0.78 设备分钟

**第一次（30 秒）**：`callbacks=[gate]` —— ms-swift 的 `args.callbacks` 只接受
**字符串名**（内部走 `callbacks_map` 查表），传实例直接 `KeyError`。

**第二次（17 秒）**：改用 `Trainer.__init__` 钩子 + `add_callback` 后，
撞上 `Seq2SeqTrainer.__init__() got an unexpected keyword argument 'tokenizer'`。

**根因是我自己造成的**：ms-swift 在 `trainers/mixin.py:124` 用

```python
trainer_parameters = inspect.signature(HfTrainer.__init__).parameters
tokenizer_key = 'processing_class' if 'processing_class' in trainer_parameters else 'tokenizer'
```

**靠检查签名**决定传 `processing_class` 还是 `tokenizer`。
我把 `Trainer.__init__` 换成 `_patched(self, *a, **kw)`，签名里就**没有 `processing_class`** 了，
ms-swift 于是退回传 `tokenizer`，在 transformers 5.x 上炸掉。

**修法**：`functools.wraps(_ORIG)(_patched)` 保住原签名。

**这次在花 GPU 时间之前做了 0-GPU 验证**：
```
原始签名含 processing_class: True
不加 wraps  -> False   ← 崩溃原因
加 wraps    -> True    ✓
```

### 5.2 教训

**门槛脚本本身从未在 GPU 上跑过，第一次真跑就暴露了两个只有真跑才会出现的问题。**
CPU 门槛证明了数据、模板、掩码、参数，但证明不了「把回调挂进 ms-swift 的 trainer」这条接线。
以后凡是**改动框架接线**的代码，要么先做不花 GPU 的等价验证，要么预期第一次会失败。
