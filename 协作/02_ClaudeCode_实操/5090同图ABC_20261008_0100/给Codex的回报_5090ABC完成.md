### 四、**本轮最重要的发现：B 的辅助字段本身是错的**

用户问"几何是不是 Python 算的"，核实后查出这条。

**是 Python 确定性计算的**（`prepare_data.py:103` → `calculate_static_features`，
全程 numpy，无模型参与）。**但"确定性"不等于"正确"。**

`radial_zone` 的定义是 **`_zone(质心半径)`——质心所在区，不是缺陷所在位置**。
对任何关于晶圆中心对称的图案，质心落在圆心，标签**靠算术塌缩成 "center"**。

**本项目自己的审计脚本早就记录了它**（`archive/local-skeleton/tools/radial_zone_audit.py`）：

> 冻结基准里 `Edge_Ring` 的中位质心半径只有 0.063，**83.7% 的样本落进 "center" 桶**。
> 模型对边缘环答 "edge" 反而被判错。

**在本次 356 张上的独立复算：**

| B 的 `filtered_defect_centroid_radial_zone` | 条数 |
|---|---|
| **center** | **313（87.9%）** |
| middle | 39 |
| edge | 4 |

**Edge_Ring 39 条，100% 被判 `center`**；而这些图的 `mean_radius_r` 中位
= **0.9421**、`defect_extent_r` 中位 = **2.0320**，远超判 edge 的 0.72 阈值。

**这不只是"B 的字段名起得不好"——是这个字段本身系统性算错。**

**对结果的解释力**：B 教给模型的辅助字段 88% 塌缩为 `center`、对边缘环 100% 标错，
几乎没有可用的空间信息。

**但这是解释，不是已证明的机制。** A/B/C 同时改变了监督内容，
本轮**无法**把"字段误导"与"监督 token 变多"分开；单种子。

三组"额外信息"的性质本就不同：

| 组 | 额外信息 | 来源与质量 |
|---|---|---|
| A | 无 | 公开原标签（`label_source=ground_truth`） |
| B | 几何 | **Python 计算**，但 `radial_zone` 系统性算错 |
| C | 描述 | **模型生成**（旧158 + GLM107 + 接续49 + GPT42 混合来源），不是 gold |

**这对项目主问题有直接影响**：那个字段本来是要给模型"空间依据"的，
结果它自己就错。**后续若还要用几何信息，须先换成测量缺陷真实位置的定义**
（审计脚本给了 `mean_radius` / `outer_extent` 两个替代口径），
**不能沿用现在这个**。这也意味着 B 组的结论**不能**推广成
"几何信息对类别识别无帮助"——本轮测的是一个算错的几何。
