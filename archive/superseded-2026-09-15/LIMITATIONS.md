## 5. RL / GRPO

- **GSPO 其实可用 —— 初版报告写错了，此处更正。** 初版依据该 ms-swift 提交的
  `rlhf_type` 枚举 `['dpo','orpo','simpo','kto','cpo','rm','ppo','grpo','gkd']`
  不含 `gspo`，即断言「GSPO 无法执行」。**这个推断是错的。**
  GSPO 在 ms-swift 里**不是**独立的 `rlhf_type`，而是 GRPO 的一个损失变体，
  由 `--importance_sampling_level sequence` 开启：
  `swift/rlhf_trainers/args_mixin.py:425` 的注释直指 GSPO 论文
  （arXiv:2507.18071），该参数文档原文为
  *"'sequence' mode averages the log probability ratios of all valid tokens in
  the sequence. The GSPO paper uses 'sequence' level for stable training."*
  该参数默认值为 `token`，**即普通 GRPO**。
  教训：只查了一个枚举名就断言某个算法不存在，而真正的开关是同文件里另一个参数。
  因此**第一次跑的是普通 GRPO，不是 GSPO**；已按论文重跑 GSPO，见 5.2。
- **无 vLLM**：环境未安装 vLLM，只能用 `--use_vllm false`（TransformersEngine），
  rollout 明显更慢；每次实验由墙钟而非步数限时。
- 冒烟已通过：2/2 步，train_runtime 40.26s，峰值显存 10,597 MiB，四个奖励函数均正常触发。
- **奖励信号高度集中于 `wafer_clock`**。正式运行 150 步完成后，按训练日志全量统计
  （源：`outputs/reports/grpo_reward_trace.txt`）：

  | 奖励 | 均值 | 平均组内标准差 | 相对信号强度 |
  | --- | --- | --- | --- |
  | `WaferFormat` | 0.9998 | **0.0005** | 可忽略（已饱和） |
  | `WaferClass` | 0.9000 | 0.0803 | 弱 |
  | `WaferRadial` | 0.8650 | 0.1180 | 中 |
  | `WaferClock` | 0.6283 | **0.2244** | **主导** |

  要点是**均值高不等于有信号**：`WaferClass` 均值 0.90，但四份采样通常都对，
  组内标准差只有 0.08；均值最低的 `WaferClock`（0.63）标准差最大，
  因而贡献了绝大部分优势。另外 **36.0% 的步里一个组内四份采样的奖励完全相同**，
  这些步的优势为 0，完全不产生梯度 —— 也就是说这次 RL 有超过三分之一的步数是空转的。
  最终数字以 `outputs/reports/grpo_train_result.json` 的 `reward_signal` 为准。
- 奖励函数全部为确定性规则（可信类别标签 + 圆拟合几何），**未使用任何 LLM-Judge 作为奖励**。
- 真实运行的结果写入 `outputs/reports/grpo_train_result.json`：150 步全部完成，
  耗时 2414s，峰值显存 14,391 MiB，平均 KL 1.1068。

### 5.1 GRPO 相对 SFT 没有实质提升

这是本轮 RL 最重要的结论，必须明说：**GRPO 在冻结基准上的表现与 SFT 基本持平，
差异落在噪声范围内。**

| 指标 | SFT | GRPO | 变化 |
| --- | --- | --- | --- |
| macro-F1 | 0.6114 | 0.6197 | +0.008（CI 大幅重叠） |
| 95% CI | [0.5496, 0.6602] | [0.5554, 0.67] | 重叠 |
| structured defect_type | 0.5840 | 0.6032 | +0.019 |
| structured radial_zone | 0.2640 | 0.2698 | +0.006 |
| robustness accuracy | 0.5622 | 0.5661 | +0.004 |
| clock MAE | **1.6847** | 1.7121 | −0.027（变差） |
| size MAE (R) | **0.4999** | 0.5695 | −0.070（变差） |
| caption must-hit | **0.7540** | 0.7222 | −0.032（变差） |
| flip rate | **0.2474** | 0.2672 | −0.020（变差） |
| retrieval mAP@10 | **0.3873** | 0.3742 | −0.013（变差） |

分类准确率两者完全相同（0.6230）。改善集中在分类与结构化字段，退化集中在
时钟/尺寸/描述/检索，两边幅度都在 1–2 个百分点量级。**因此不应宣称 RL 阶段有收益。**

**上表 clock MAE 一行需要额外打折**：SFT 只在 203 行上算出、GRPO 只在 198 行上算出，
两个**子集并不相同**（见 6.8）。对两个不同总体计算出的 MAE 直接相减本身就不成立，
所以「1.6847 → 1.7121 变差」只能读作噪声，不能读作退化。其余各行是在同一批样本上
计算的，不受此影响。
这一结果与上面的奖励信号分析一致：唯一有明显方差的 `WaferClock` 并没有让 clock MAE 变好，
说明该奖励的部分分**未能转化为基准上的更好估计**；同时 36% 的步数因组内奖励全同而空转，
且 150 步的 KL 漂移（均值 1.11）本身可能抵消了有限的学习信号。
若要真正验证 RL 的价值，需要更大的 rollout 多样性（更多 generation、更高温度）
或一个方差更大的奖励设计，这超出了本次的时间预算。

### 5.2 GSPO：梯度信号确实变好了，基准成绩确实变差了

论文指定的是 GSPO，而 5.1 跑的是普通 GRPO，因此按论文补跑。做法不是换脚本，
而是把 `--importance_sampling_level` 从默认的 `token` 改成 `sequence`（见 §5 首条），
**其余超参逐字不动**，这样两个 run 的差异是一个有文档记录的开关，而不是一份被改过的脚本。

**一个必须记下的偏离：组大小从论文的 32 降到 8。** ms-swift 要求
`generation_batch_size` 能被 `num_generations` 整除；本环境无 vLLM（见 §7），
一次前向要真跑 `num_generations × generation_batch_size` 次生成，G=32 意味着
每个优化步约 1024 次生成、约 17 分钟，150 步要 40 小时以上，**在这台机器上不可行**。
这是资源约束，不是设计选择，因此这里的 GSPO **不是论文设定的复现**，
只能读作「在同一预算下 GSPO 相对 GRPO 的表现」。

**奖励信号：基本没有变化。** 初版这里写的是「GSPO 明显优于 GRPO」，
**那是错的，现撤回。** 当时引用的「零优势步 13.3%」**不是任何文件里的统计量**：
训练记录只保存 first/last 两步，而这两步恰好一个 0.0、一个 1.0，
我把其中一步的值当成了 150 步的均值，并据此写了一整段结论。
按完整 150 步重新实测（`logs/24_grpo_*.log`，每 run 各自的日志）：

| | GRPO | GSPO (lr 5e-5) |
| --- | --- | --- |
| 零优势步占比（组内奖励全同 → 不产生梯度），实测均值 | 36.00%（54/150 步） | **38.00%（57/150 步）** |
| `WaferClass` 组内标准差 | 0.0803 | 0.0855 |
| `WaferFormat` 组内标准差 | 0.0005 | 0.0132 |
| `WaferRadial` 组内标准差 | 0.1180 | **0.0528** |
| `WaferClock` 组内标准差 | 0.2244 | 0.2306 |

`frac_reward_zero_std` 是**双峰**的：每一步要么整组奖励完全相同（记 1.0），
要么组内不同（记 0.0），因此均值直接就是「空转步数占比」。
**结论是 GSPO 的空转步数没有下降，反而多了 3 步。** 四个奖励里只有
`WaferFormat` 从饱和（0.0005）变得略有区分度，而 `WaferRadial` 的组内标准差**反而减半**，
合起来是一次平手而非改善。

因此 **5.1 里「问题出在组大小」的推断在本轮没有得到支持**：
序列级归一化单独并不足以恢复组内方差。组大小这条路径本轮没有被检验
（G=32 在本环境不可行），所以既不能说它对，也不能说它错。

**但基准成绩是实打实的下降**，且幅度远大于 5.1 里的那些漂移：

| 指标 | SFT | GRPO | GSPO (lr 5e-5) |
| --- | --- | --- | --- |
| 分类准确率 | 0.6230 | 0.6230 | **0.5397** |
| macro-F1 | 0.6114 | 0.6197 | **0.5014** |
| macro-F1 95% CI | [0.5496, 0.6602] | [0.5554, 0.6704] | **[0.4367, 0.5537]** |
| structured defect_type | 0.5840 | 0.6032 | 0.5635 |
| structured radial_zone | 0.2640 | 0.2698 | 0.3056 |
| clock circular MAE | 1.6847 | 1.7121 | **1.9519** |
| size MAE (R) | 0.4999 | 0.5695 | **0.6927** |
| caption must-hit | 0.7540 | 0.7222 | **0.6627** |
| robustness accuracy | 0.5622 | 0.5661 | **0.5146** |
| flip rate | 0.2474 | 0.2672 | 0.2354 |

这里必须先纠正一处我自己写错的地方：初稿曾写「GSPO 的置信区间与 SFT 不重叠，
因此下降显著」。**这是错的。** GSPO 的 95% CI 上界 0.5537，SFT 下界 0.5496，
两者**擦边重叠**了 0.0041。按这个 CI 判定，**不能宣称下降在 95% 水平上显著** ——
`tools/final_report.py` 正是按 `ci[1] < sft_ci[0]` 自动判定的，它给出的结论是「与 SFT 重叠」，
与我手写的那句话相反；我采用了工具的结果。
（教训与本项目其他几处一致：手写的数字必须由代码复核，否则会写出方向相反的话。）

**但也不应按 5.1 那样的「纯噪声」处理。** 区别在于幅度与一致性：
GRPO 相对 SFT 是 ±0.01~0.03 的双向漂移，而 GSPO 是 **−0.1101 的单向下降**，
且除 `radial_zone` 外**每一项指标都同向变差**。诚实的表述是：
**幅度大到有实际意义，但按本次的 CI 判定达不到统计显著，因此只能说「明显更差」，
不能说「显著更差」。** `radial_zone` 那一格略高，但该指标本身是标签退化的（见 §6.7），
不足以抵消其余各项一致的下降。

**不能把这次下降直接归给 GSPO 算法本身 —— 这个 run 一次动了两个量。**
为了对齐论文，学习率同时从 GRPO 用的 1e-5 提到了论文的 5e-5（5 倍），
平均 KL 达到 1.0217。算法与学习率耦合在一起，单看这个 run 无法区分。
因此又补跑了一个 **GSPO + lr 1e-5**（只让学习率与 GRPO 一致，算法保持 sequence），
正是为了把两者拆开；该 run 结果见 `outputs/reports/gspo_lr1e5_train_result.json`
与对比表中的 `GSPO_lr1e5` 列。

**结论（按论文自己 §8.11 的判定门槛）**：论文该节写的是
「若提升落在置信区间内，结论写『未观察到显著提升』，不写『RL 有效』」，
并且给出分支「F -- 否 --> G[保留 SFT 为最终模型]」。GSPO 的基准表现低于 SFT，
落入该分支，因此：

> **最终模型保留 SFT（`outputs/checkpoints/qwen35_9b_qlora_v1`）。**
> GSPO 与 GRPO 均**未观察到相对 SFT 的显著提升**；GSPO 在本文预算下反而明显更差。
> 不写「RL 有效」。

需要说清的是，这**不等于**「GSPO 不如 GRPO」。本文的 GSPO 组大小只有论文的 1/4，
且学习率是按论文设定而非按本模型规模调过的，这两个因素都可能单独造成退化。
诚实的表述是：**在本文可用的预算与超参下，GSPO 既没有带来基准收益，
也没有在梯度层面显示出优势（空转步 36.0% → 38.0%，见上）。**
初版曾据一个被误读的单步数字声称 GSPO 改善了学习信号，该说法已撤回。
要判定算法本身的优劣，需要 G=32 或学习率扫描，两者都超出本次时间预算。

### 6.1 Base 与随机不可区分

| 基线 | accuracy | macro-F1 | 来源 |
| --- | --- | --- | --- |
| 多数类 | 0.1190 | 0.0236 | `trivial_baselines.json` |
| 均匀随机（5 seed） | 0.1230 ± 0.0144 | 0.1211 | 同上 |

Base 的 macro-F1 置信区间**覆盖**随机基线 0.1211，即零样本 Base 在 macro-F1 上与

### 6.2 两个结构化字段低于「恒答基线」——看似提升，实为未学会

初版评测只给分类与检索算了平凡基线，漏掉了结构化字段，而漏掉的正是最关键的对照。
补算后（`outputs/reports/structured_baselines.json`）：

| 字段 | 恒答基线（完全不看图） | Base | SFT | GRPO | 结论 |
| --- | --- | --- | --- | --- | --- |
| `defect_type` | 0.1190 | 0.2103 | **0.5840** | **0.6032** | 显著超过基线 |
| `radial_zone` | **0.8333** | 0.0794 | 0.2640 | 0.2698 | **全部未超过** |
| `clock_sector`（MAE↓） | 2.6932 | 5.0000 | **1.6847** | **1.7121** | SFT/GRPO 超过，Base 未超过 |
| `size_r`（MAE↓） | **0.1101** | 1.2139 | 0.4999 | 0.5695 | **全部未超过** |

含义必须说清楚：

- `radial_zone` 有 83% 的样本是 `center`，所以**永远回答 `center` 就能得 0.8333**。
  SFT 的 0.2640 和 Base 的 0.0794 都远低于这个下限。
  **但这一点需要重大修正，见 6.7**：这个 0.8333 的下限来自一个退化的标签，
  它衡量的是缺陷「质心」落在哪一带，而不是缺陷落在哪一带。对称图案（边缘环、
  随机分布、满片）的质心必然在圆心，于是标签被算术地压成 `center`。
  因此不能说模型「还不如不看图」——它回答的是另一个、更合理的问题。
  修正标签后模型的表现是**接近随机**（0.4560 vs 下限 0.5079），而不是远低于下限。
- `size_r` 则是一项**经得起推敲的真实失败**：模型预测与真值的相关系数仅 **0.0382**，
  即基本不含该字段的信息。它给出了 88 个不同取值（不是恒答），中位数 1.964 接近
  真值中位数 2.031，但散布与真值无关，于是 MAE 0.4999 反而大于恒答中位数的 0.1101。
  **这不是标签问题，是这个字段没有被学会。**
- `clock_sector` 是唯一一个微调后超过恒答基线的几何字段（1.6847 < 2.6932）。
  **但这一行有两个问题，见 6.8**：该 MAE 只覆盖 203/250 个样本，被排除的正是
  最难评分的那两类；而 Base 那一格的 5.0000 **只在 1 个样本上算出**（其余 251 行
  全部因解析失败被跳过），因此「Base 甚至差于均匀随机 3.0」不成立，该格应视为未测。
- 因此**不能声称模型学会了完整的结构化输出**：它学会了 `defect_type`，
  时钟方向有部分信号（但需按 6.8 打折），径向分区与尺寸没有学会。

这说明规格要求「随机/majority 基线」是必要的：没有基线，这两行会被当成改进写进结论。
本项目的基线现已覆盖分类、检索与结构化字段。**同时它也说明只有基线还不够：
基线本身必须建立在一个测量了它声称要测量的东西的标签上（6.7）。**

### 6.3 检索是下限而非调优结果

- 检索随机地板：mAP@10 0.0330 / nDCG@10 0.0596 / Recall@10 0.0394。
- 检索向量取自**固定 probe 的 mean-pooled 末层隐状态**，未经任何检索专项训练。
  因此所得指标应读作**下限**，不代表该模型在检索上的能力上限。
- GRPO 的检索同样是先把 adapter 合并为 bf16 再用同一 probe 打分
  （`models/Qwen3.5-9B-grpo-v1-merged`），与 Base/SFT 走完全相同的路径，
  否则三列不可比。合并后目录结构与已通过等价性校验的 SFT 合并模型一致。

### 6.4 训练/服务提示词不一致（基准低估 SFT）

- 基准的分类提示词与 SFT 训练时的提示词不同：基准无 system message 且措辞不同。
- SFT 在冻结基准上 accuracy 0.6230 / macro-F1 0.6114；
  在**训练格式**提示词上 accuracy **0.8849** / macro-F1 **0.8882**（95% CI [0.8492, 0.9223]）。
- 即基准数字**低估**了 SFT 的实际能力，差距来自提示词不一致而非模型能力。
- 该不一致**有意未在运行中途修改**，因为修改会使 Base 与 SFT 不再可比。
  上表训练格式数字是**诊断**，不作为榜单成绩引用。

### 6.5 约 2 个样本的评测差异

SFT accuracy 在完整基准上为 0.6230，在辅助分类集上为 0.63095，相差 2 个样本，
归因于批次组成与 padding 差异。与 6.6 是同一类数值噪声。

### 6.6 融合等价性：精确一致率 != 1.0 不代表失败

| 比较 | 行数 | 精确一致 | 功能一致 | 来源 |
| --- | --- | --- | --- | --- |
| **同一 adapter** 4bit vs bf16（噪声地板） | 60 | 0.4333 | 0.7000 | `outputs/merge_check/precision_floor.json` |
| adapter vs merged | 60 | 0.4667 | **0.7667** | `outputs/merge_check/equivalence.json` |
| merged vs merged（重跑，确定性） | — | 1.000 | 1.000 | 同上 |

答案是自由文本（caption/JSON），一个 token 的舍入差异会级联影响后续生成，
因此**精确字符串一致率衡量的是数值可复现性，不是正确性**。
关键结论：**merged 与 adapter 的偏离（0.7667）小于同一 adapter 单独改变精度的偏离（0.7000）**，
故融合是忠实的。不可把 `exact < 1` 读作"融合失败"。
比较仅在 60 行子集上进行，未覆盖全部 1512 行。

### 6.7 `radial_zone` 标签退化：它测的是「质心」而不是「位置」

这是本轮复核中**最重要的一项更正**，它推翻了 6.2 初版对 `radial_zone` 的判断。

`utils.py:139` 的规则是：

```python
def _zone(radius_ratio):
    if radius_ratio < 0.35: return "center"
    if radius_ratio < 0.72: return "middle"
    return "edge"
```

而特征里写的是 `"radial_zone": _zone(centroid_r)` —— **缺陷像素质心的半径**。
对任何关于圆心对称的图案，质心就在圆心，于是标签被算术地压成 `center`，
与缺陷实际在哪一带无关。实测（`benchmarks/wafer_bench_v1/structured.jsonl`）：

| 真实缺陷类型 | 中位质心半径 | 推出的标签 |
| --- | --- | --- |
| `Edge_Ring`（边缘环） | **0.063** | center |
| `Near_full`（满片） | 0.050 | center |
| `Random`（随机散布） | 0.044 | center |
| `Donut`（环） | 0.157 | center |
| `Edge_Loc`（边缘局部） | 0.333 | center（恰好卡在 0.35 阈值下） |

一个**贴在晶圆边缘的环**，质心半径只有 0.063，标签因此是 `center`。
全基准 **83.7%** 落在 `center` 桶里，全部是这一个机制造成的。

用 `outputs/reports/radial_zone_audit.json`（已先在 manifest 上验证与金标逐位一致，
251/251 精确相符、最大偏差 0）重新评分：

| 判据 | 金标分布 | 下限 | Base | SFT | GRPO |
| --- | --- | --- | --- | --- | --- |
| `centroid`（现状，质心） | center 210 / middle 36 / edge 5 | 0.8333 | 0.0794 | 0.2640 | 0.2698 |
| `mean_radius`（缺陷像素平均半径） | edge 123 / middle 128 | 0.5079 | 0.1310 | **0.4560** | 0.4444 |
| `outer_extent`（外沿半径） | edge 251 | 0.9960 | 0.1706 | 0.4200 | 0.4206 |
| `curate_rule`（本项目自己的验收规则） | — | 0.8333 | 0.1032 | 0.3240 | 0.3333 |

两点结论：

1. **换用「缺陷落在哪一带」的标签后，SFT 从 0.2640 升到 0.4560，下限同时从
   0.8333 降到 0.5079。** 说明模型的回答与「缺陷的位置」远比与「质心的位置」吻合，
   `radial_zone` 上 0.2640 这个数字**主要反映标签的毛病，而不是模型的毛病**。
2. **但换标签后模型仍然没有超过下限**（0.4560 < 0.5079），而且 `mean_radius`
   只有两个取值、随机水平就是 0.5。所以正确说法是：
   **模型在这个字段上接近随机，既不是「学会了」，也不是初版说的「远差于不看图」。**

另有一处词汇不一致：`prompts.py:56` 要求模型在
`center|middle|edge|full|none` 五值中作答，而 `_zone()` **永远不会返回 `full`**，
金标里 `full` 出现 0 次。SFT 有 **69/250**、Base 有 **189/252** 次回答 `full`，
这些**在构造上不可能得分**——模型使用了提示词明确提供的取值而被判错。

### 6.8 时钟 MAE 存在幸存者偏差，且被排除的正是最难的一类

`evaluate.py` 的 `clock_error` 用 `int(predicted)` 取值，失败即返回 `None`，
`structured_metrics` 随后**跳过该行**。所以公布的 MAE 是在「能解析的行」上算的。
被丢弃的答案实测为 `"all"` 与 `"none"` —— 模型在说「这个缺陷绕满一圈」或
「没有方向可言」。这是对提问的合理回答，却无法与单扇区金标打分。
来源：`outputs/reports/clock_parse_audit.json`。

SFT 丢弃 **47/250 = 18.8%**，且丢弃**不是随机的**：

| 类别 | 丢弃率 | |
| --- | --- | --- |
| `Random`（随机散布，无方向） | **24/30 = 0.80** | 过度集中 |
| `Edge_Ring`（闭合环，绕满 360°） | **18/30 = 0.60** | 过度集中 |
| 其余七类 | 0.00 – 0.12 | |

也就是说：**被排除的恰好是「单一钟点方向本就没有意义」的两类**，
保留下来的 203 行集中在方向确实良定义的类别上。因此 1.6847 这个数字
**是条件于一个比基准更容易的子集**，真实值应更差。GRPO 丢弃更多（54/252 = 21.4%）。

Base 更极端：**丢弃 251/252 = 99.6%，仅剩 1 行计分**，且九个类别的丢弃率全是 1.00 ——
Base 几乎一律回答 `all`/`none`。所以 Base 的时钟 MAE 5.0000 实际上是**在单个样本上**
算出来的，它「差于均匀随机 3.0」这一说法不成立，**不应作为任何对比的依据**。

**更正方向**（本次未实施，记录以免误读）：应当把「无方向」作为合法答案处理，
例如对 `Edge_Ring`/`Random`/`Near_full` 允许 `all`/`none` 并计入正确，
或将该字段改为方向性度量（`resultant_length`）而不是单扇区。

## 8. 已修复但值得记录的缺陷（均为"静默产生貌似合理结果"类型）

1. **`tools/retrieval_rank.py` 曾产出纯文本 embedding。**
   直接传字符串给 processor 仍会返回 `pixel_values`，但 `input_ids` 中**没有**
   `<|image_pad|>` 视觉 token（实测 seq_len 10、视觉 token 0），视觉塔输出无处可去。
   返回类型完全正常，检索指标却是无意义的。已改用 `apply_chat_template`（seq_len 218、
   196 个视觉 token，与 ms-swift 侧实测一致）并加入硬断言 + `tests/test_retrieval_embed.py`。
2. **`tools/error_cases.py` 曾因 swift infer 不写回 `sample_id` 而错位配对**，
   导致准确率报成 0.0 / 0.0317。已改为先在完整请求表上对齐、再按任务过滤，
   修复后精确复现基线准确率 0.21428571428571427。
3. **`scripts/24_train_grpo.sh` 的 adapter 解析曾在 `set -e` 下静默中止。**
   循环最后一次迭代是 `checkpoint-604-merged`，`[ -f ]` 测试失败使循环返回 1，
   `pipefail` 将其传出，赋值语句触发 `set -e` 而**在打印任何输出之前**终止脚本 ——
   表现为退出码 1、日志 0 字节、无 Python 进程。已改用 `find`（恒返回 0）。
4. **曾把一个单步日志值当作 150 步的均值，并据此写出了方向相反的结论。**
   GSPO 训练记录只保存 `first_step` / `last_step` 两步，而 `frac_reward_zero_std`
   这两步恰好一个是 `0.0`、一个是 `1.0`。我取了其中一步的值，当作「GSPO 的零优势步占比」，
   与 GRPO 的实测均值 36.0% 相比，得出「GSPO 把空转步从 36% 降到 13%、
   序列级归一化改善了梯度信号」的结论，并已写进 §5.2 初稿。
   **按完整 150 步实测，真实值是 38.00%（57/150 步）—— 不但没降，反而更高。**
   已撤回该结论，并把统计函数改为读取每 run 自己的完整日志、返回
   `(占比, 空转步数, 总步数)`，使「57/150」这类可核对的形式直接进报告，
   而不是只剩一个无法追溯的小数。教训：**从一个只存首末两项的记录里取「均值」，
   取到的必然不是均值；跨 run 比较前必须确认两边的统计口径与样本范围一致。**
5. **两个 RL run 共用同一个外层日志，后跑的覆盖了先跑的。**
   `scripts/29_grpo_train.sh` 的 `RUN_TAG` 默认值为 `grpo`，第一次 GSPO 运行沿用了该默认值，
   于是 `logs/29_grpo_train.log` 被 GSPO 覆盖，而 `grpo_train_result.json` 的 `log`
   字段仍指向它。任何按该字段回溯 GRPO 原始日志的操作，都会**静默地读到 GSPO 的数据**。
   已把两条记录的 `log` 改指向各自 run 的内部日志 `logs/24_grpo_<RUN>.log`
   （该文件按 run 命名，未被共用），并在记录里留下 `log_note` 说明改指原因。

这几处的共同点：**失败被伪装成正常结果** —— 返回类型正常、数字看起来合理、
不报任何错。记录在此以免复现。

**本轮复核又发现两处同类问题，但属于「已定位、未修复」，故记在第 6 节而非此处：**
第 6.7 节的 `radial_zone` 退化标签（一个测量质心却被当作测量位置的字段，
值域上还比提示词少一个取值），以及第 6.8 节的时钟幸存者偏差（一个在
「能解析的子集」上计算、且该子集系统性地排除了最难类别的指标）。
两者的共性与前三条完全相同：**产出了看起来正常、可以直接引用的数字**。
之所以没有就地修改，是因为改动评测定义会使已公布的 Base/SFT/GRPO 三列不再可比；
正确做法是在冻结基准的下一版中一并修正并重跑，而不是事后只改分数。
