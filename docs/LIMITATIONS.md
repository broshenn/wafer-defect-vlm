## 5. RL / GRPO

- **GSPO 其实可用 —— 初版报告写错了，此处更正。** 初版依据该 ms-swift 提交的
  `rlhf_type` 枚举 `['dpo','orpo','simpo','kto','cpo','rm','ppo','grpo','gkd']`
  不含 `gspo`，即断言「GSPO 无法执行」。**这个推断是错的。**
  GSPO 在 ms-swift 里**不是**独立的 `rlhf_type`，而是 GRPO 的一个损失变体，
  由 `--importance_sampling_level sequence` 开启：
  `swift/rlhf_trainers/args_mixin.py:425` 的注释直指 GSPO 论文
  （arXiv:2507.18071），该参数文档原文为
  *"'sequence' mode averages the log probability ratios of all valid tokens in
  the sequence. The GSPO paper uses 'sequence' level for stable training."*
  该参数默认值为 `token`，**即普通 GRPO**。
  教训：只查了一个枚举名就断言某个算法不存在，而真正的开关是同文件里另一个参数。
  因此**第一次跑的是普通 GRPO，不是 GSPO**；已按论文重跑 GSPO，见 5.2。
- **无 vLLM**：环境未安装 vLLM，只能用 `--use_vllm false`（TransformersEngine），
  rollout 明显更慢；每次实验由墙钟而非步数限时。
- 冒烟已通过：2/2 步，train_runtime 40.26s，峰值显存 10,597 MiB，四个奖励函数均正常触发。
- **奖励信号高度集中于 `wafer_clock`**。正式运行 150 步完成后，按训练日志全量统计
  （源：`outputs/reports/grpo_reward_trace.txt`）：

  | 奖励 | 均值 | 平均组内标准差 | 相对信号强度 |
  | --- | --- | --- | --- |
  | `WaferFormat` | 0.9998 | **0.0005** | 可忽略（已饱和） |
  | `WaferClass` | 0.9000 | 0.0803 | 弱 |
  | `WaferRadial` | 0.8650 | 0.1180 | 中 |
  | `WaferClock` | 0.6283 | **0.2244** | **主导** |

  要点是**均值高不等于有信号**：`WaferClass` 均值 0.90，但四份采样通常都对，
  组内标准差只有 0.08；均值最低的 `WaferClock`（0.63）标准差最大，
  因而贡献了绝大部分优势。另外 **36.0% 的步里一个组内四份采样的奖励完全相同**，
  这些步的优势为 0，完全不产生梯度 —— 也就是说这次 RL 有超过三分之一的步数是空转的。
  最终数字以 `outputs/reports/grpo_train_result.json` 的 `reward_signal` 为准。
- 奖励函数全部为确定性规则（可信类别标签 + 圆拟合几何），**未使用任何 LLM-Judge 作为奖励**。
- 真实运行的结果写入 `outputs/reports/grpo_train_result.json`：150 步全部完成，
  耗时 2414s，峰值显存 14,391 MiB，平均 KL 1.1068。

### 5.1 GRPO 相对 SFT 没有实质提升

这是本轮 RL 最重要的结论，必须明说：**GRPO 在冻结基准上的表现与 SFT 无可测差异。**
成对检验（同一批 252 行）把这一点钉得更死：准确率差 +0.0000，
95% CI [-0.0317, +0.0317] 含 0，McNemar `p` = 1.00 —— 不是「差异小」，
是**在这个样本量下量不出来**。

| 指标 | SFT | GRPO | 变化 |
| --- | --- | --- | --- |
| macro-F1 | 0.6114 | 0.6197 | +0.008（CI 大幅重叠） |
| 95% CI（边际）| [0.5496, 0.6602] | [0.5554, 0.6704] | 重叠 |
| structured defect_type | 0.5840 | 0.6032 | +0.019 |
| structured radial_zone | 0.2640 | 0.2698 | +0.006 |
| robustness accuracy | 0.5622 | 0.5661 | +0.004 |
| clock MAE | **1.6847** | 1.7121 | −0.027（变差） |
| size MAE (R) | **0.4999** | 0.5695 | −0.070（变差） |
| caption must-hit | **0.7540** | 0.7222 | −0.032（变差） |
| flip rate | **0.2474** | 0.2672 | −0.020（变差） |
| retrieval mAP@10 | **0.3873** | 0.3742 | −0.013（变差） |

分类准确率两者完全相同（0.6230）。改善集中在分类与结构化字段，退化集中在
时钟/尺寸/描述/检索，两边幅度都在 1–2 个百分点量级。**因此不应宣称 RL 阶段有收益。**

**上表 clock MAE 一行需要额外打折**：SFT 只在 203 行上算出、GRPO 只在 198 行上算出，
两个**子集并不相同**（见 6.8）。对两个不同总体计算出的 MAE 直接相减本身就不成立，
所以「1.6847 → 1.7121 变差」只能读作噪声，不能读作退化。其余各行是在同一批样本上
计算的，不受此影响。
这一结果与上面的奖励信号分析一致：唯一有明显方差的 `WaferClock` 并没有让 clock MAE 变好，
说明该奖励的部分分**未能转化为基准上的更好估计**；同时 36% 的步数因组内奖励全同而空转。

本节初稿在这里还写过一句「150 步的 KL 漂移（均值 1.11）本身可能抵消了有限的学习信号」，
**该句已删除**：5.2.2 核出 `kl` 是逐 token 均值，而不同配置的补全长度差 5%–15%，
这个量在本设计里**连方向都判不出来**，因此不能拿它解释「为什么没有增益」。
用同一个不可判向的量，在 5.2.2 里解释退化、在这里解释无增益，是同一处错误的两面。
若要真正验证 RL 的价值，需要更大的 rollout 多样性（更多 generation、更高温度）
或一个方差更大的奖励设计，这超出了本次的时间预算。

### 5.2 GSPO：两个错的结论，和那个真正起作用的变量

论文指定的是 GSPO，而 5.1 跑的是普通 GRPO，因此按论文补跑。做法不是换脚本，
而是把 `--importance_sampling_level` 从默认的 `token` 改成 `sequence`（见 §5 首条），
这样两个 run 的差异是一个有文档记录的开关，而不是一份被改过的脚本。

本节记录 GSPO 的组大小 × 学习率网格：组大小 8 的两个（学习率分别取论文的 5e-5
与 GRPO 的 1e-5）、论文设定的 G=32（lr 5e-5），以及补齐网格第四角用的
G=32 + lr 1e-5 —— 最后这一条给出的是**同一组大小、同一算法、只改学习率**的对照
（G=8 那一对也是同一种对照）。它已经跑完（run 41）并已并入本节：
5.2.2 的四条对照、5.2.4 的 KL 与长度表、5.2.5 的类别表都含它的结果。
**初稿在这里写过它「唯一能把「组大小」与「IS 层级」分开」—— 那句是错的**：
两条都是 sequence，改的是组大小；而紧接的这一段会说明，本设计连「只改组大小」
都没有做到（组大小一变，有效批次跟着按平方变）。它能分开的是学习率。
**其中「G=32」这一条，是我先断言不可行、后被实测推翻的。**

**本节有一个贯穿全部「组大小」读数的混淆，在此单独说明。**

训练记录里的 `grad_accum` 字段是**写死的常量 4**，不是实测值。因此它既显示不出、
也掩盖不了这个事实：**每个 run 的梯度累积都设成了与组大小相等**（4/4、8/8、32/32）：

| 组大小 | 真实累积步 | 有效批次（= 组大小 × 微批次 1 × 累积步）|
| --- | --- | --- |
| G=4 | 4 | 16 |
| G=8 | 8 | 64 |
| G=32 | 32 | **1024** |

**有效批次按组大小的平方增长，所以本设计里从来没有单独改过组大小**：
G=8 → G=32 是组大小 4 倍、有效批次 **16 倍**。5.2.5 的「加组大小」一行、
以及 `group_size_paired` 的全部成对对照，比较的都是同时变了两个量的两个 run，
**因此它们不能把差异归给组大小**。

这是与 5.2.2 的 IS 层级混淆**相互独立**的第二个混淆（token 永远是 G=4、
sequence 永远是 G=8 或 G=32）。两个合起来：本设计**既没有单独变过 IS 层级，
也没有单独变过组大小** —— 论文的两个关键量与别的东西绑在了一起。

**学习率的对照不受影响**，这一点必须说清楚，以免这条更正顺手削弱了好结果：
它们在同一个组大小内比较，累积步与有效批次都固定（G=4 两个学习率、
G=8 两个学习率、G=32 两个学习率）。**本节关于学习率的结论照旧成立。**

逐 run 的真实配置由训练日志里的 swift 参数还原、与记录逐条对照，见
`outputs/reports/effective_batch_correction.json`；写死字段这一点列入第 8 节第 11 条。

#### 5.2.1 两个我先写错、后被实测推翻的结论

**其一：「GSPO 无法执行」。** 依据是该 ms-swift 提交的 `rlhf_type` 枚举
`['dpo','orpo','simpo','kto','cpo','rm','ppo','grpo','gkd']` 不含 `gspo`。
这是错的 —— GSPO 不是独立的 `rlhf_type`，而是 GRPO 的损失变体，
由 `--importance_sampling_level sequence` 开启（证据见 §5 首条）。
**因此第一次跑的是普通 GRPO，不是 GSPO。**

**其二：「论文的 G=32 需要 40 小时以上，本环境不可行」。**
这个数字**从未被测量过**，来源是一个错误假设：把 `generation_batch_size` 当成 prompt 数，
于是算出每步 32×32=1024 次生成。而 ms-swift 在第一次启动失败时给出的报错
（`generation_batch_size (4) must be evenly divisible by num_generations (16)`）
已经说明它是按 **completion** 计数的，所以每步只有 32 次生成。
真正的证据当时就在日志里，被我跳过了。

实测（`SMOKE=1 NUM_GENERATIONS=32 GRAD_ACCUM=32`，2 步）：

| | G=4 | G=8 | **G=32（实测）** |
| --- | --- | --- | --- |
| 步时 | 16.1s | 21.2s | **60–62s** |
| 150 步预计 | 0.7h | 0.9h | **约 2.5h** |
| 峰值显存 | 14,391 MiB | 14,617 MiB | **15,185 MiB** |

**论文的组大小在这台机器上完全跑得动，我原来的结论错了约 17 倍。**
G=32 的正式 run 因此在报告定稿前启动（`RUN_TAG=qwen35_9b_gspo_g32`，
G=32 / lr 5e-5 / sequence），结果并入 5.2.3。

教训：**「不可行」和「已测量」是同一等级的断言，没有实测就不能写成结论。**
本项目已有多处同类错误（见 §8），这是又一处，且这次错在**把一条已有的证据读漏了**。

#### 5.2.4 判定

按论文自己 §8.11 的门槛（「若提升落在置信区间内，结论写『未观察到显著提升』，
不写『RL 有效』」，分支「F -- 否 --> G[保留 SFT 为最终模型]」）：

> **最终模型保留 SFT（`outputs/checkpoints/qwen35_9b_qlora_v1`）。**
> GRPO 与 GSPO（两个学习率、两个组大小）均**未观察到相对 SFT 的显著提升**。
> 不写「RL 有效」。

需要说清的是，这**不等于**「GSPO 不如 SFT」或「GSPO 不如 GRPO」：
在 lr 1e-5 上 GSPO、GRPO 与 SFT 两两都落在噪声内；在 lr 5e-5 上两个算法都
**显著低于** SFT（5.2.2），但它们彼此之间仍分不开。**算法不是差异的来源。**

诚实的表述是：**在本模型规模与本次预算下，RL 阶段仍然没有产生可测的
基准增益，而且在高学习率档上产生了可测的基准损失**；这条在 run 45 落地后
需要说清楚：macro-F1 的**点估计**最高的现在已经是 GSPO(G=4) lr1e-5 的 0.6255（SFT 0.6114），
而**成对检验**对 SFT 仍不排除 0（Δ准确率 +0.0040、`p` = 1.0）—— 点估计动了，可测的增益没有动，
两者不是同一句话。空转步在 lr 1e-5 的 GSPO 上确实
大幅少于 GRPO（36.00% → 15.33%），但那个对照同时改了组大小，所以它是
**观察到的差异，不是归因给序列级归一化的证据**（5.2.3）。

八个 RL run 里有 3 个 macro-F1 点估计高于 SFT：GSPO(G=4) lr1e-5（0.6255 对 0.6114）、GRPO(G=4) lr1e-5（0.6197 对 0.6114）、GSPO(G=32) lr1e-5（0.6143 对 0.6114），
成对检验下这三个都仍与 SFT 无法区分（GSPO(G=4) lr1e-5 Δ准确率 +0.0040、`p` = 1.0；GRPO(G=4) lr1e-5 Δ准确率 +0.0000、`p` = 1.0；GSPO(G=32) lr1e-5 Δ准确率 -0.0040、`p` = 1.0）；
GRPO lr5e-5 与 lr 5e-5 的三个 GSPO run（G=4 0.4910、G=8 0.5014、G=32 0.5403）
都低于 SFT，其中论文的原始设定 G=32 + lr 5e-5 为 0.5403（见 5.2.5）。
  但短名单里 GRPO(G=4) lr1e-5 的那个点估计是**单次抽样**：该配置换种子重跑（run 42）后 macro-F1 为 0.5934，**低于 SFT 的 0.6114**。所以这句话没有错，它只是不能读成「这个配置高于 SFT」（见 5.2.7）。它的成对检验本来也分不开：Δ准确率 +0.0000、`p` = 1.0。

#### 5.2.5 G=32：论文的组大小救不回论文的学习率

G=32 + lr 1e-5（run 41，已跑完：组大小在 lr 1e-5 上分不开，+0.0040、`p` = 1.0，见 5.2.6）。

#### 5.2.7 第二个种子：本项目的噪声地板

上面每一条结论都是「跑两个**不同配置**，比较」。显著性回答的是「这个差值超出 252
行基准能分辨的范围了吗」—— 一个关于基准大小的问题。它**不**回答读者会问的那个问题：
同一套配置换个随机种子再跑一次，分数会动多少？如果那个动的幅度和要主张的效应差不多，
那效应就没有被建立起来，`p` 值再小也一样。**基准固定、种子在变**，所以基准上的 `p`
值对种子变异什么也没说。

run 42 把 GRPO(G=4, lr 1e-5) 换种子（3407 → 3408）重跑，但**这不是单变量对照**：两份训练记录的配置里另有 `algorithm`、`algorithm_note`、`gspo_note`、`importance_sampling_level_source`、`seed`、`seed_source` 不同，所以下面这条差值里混着它们。

**它不作为本文件里那几张表的一列。** 那些表列的是**配置**，而 run 42 与
GRPO(G=4) lr1e-5 是同一套配置的第二个种子；把它们并列成两列，读者会读成两个配置。
所以上面表格的 run 数不含它，它的数值只在这一节给出（`comparison.md` 里它是单独
一行，名字里带 `_s2`）。

- 准确率：seed1 **0.6230**、seed2 **0.6071**，Δ = **-0.0159**，95% 区间
  **[-0.0437, +0.0119]**（包含 0）、McNemar `p` = 0.42395。
- 参照量：GRPO 内部的学习率效应（lr5e-5 − lr1e-5，seed 1）准确率 Δ = **-0.0556**。
- 比值 **0.286** < 预设阈值 **0.5** ⇒ 按同一条规则，学习率效应**大于**种子噪声，5.2.2 的结论不被这一项推翻。
- 对 SFT 的结论是否复现：not reproducible: the two seeds land on opposite sides of SFT (+0.0000 and -0.0159), so the seed moves the comparison by more than the comparison resolves（seed1 Δ = +0.0000、`p` = 1.00000；seed2 Δ = -0.0159、`p` = 0.34375）。
- 记录里另外几项（其 `structured_and_caption` 块）：structured radial_zone Δ = +0.0062（学习率效应 +0.0754、比值 0.082)；structured clock MAE Δ = +0.0453（学习率效应 +0.2609、比值 0.174)；structured size MAE Δ = +0.1516（学习率效应 +0.3601、比值 0.421)；caption must_hit Δ = -0.0198（学习率效应 -0.1706、比值 0.116)。这几项记录只做了数值
  比较、没有逐行检验，所以上面的比值只能当**量级**看，不能当检验结论读。
- 两次抽样的 macro-F1 分别是 **0.6197** 与 **0.5934**（SFT 0.6114），第二次低于 SFT 的 0.6114 —— 第二次**低于** SFT，而 5.2.4 的短名单里就有它。那句话没有错（它说的是点估计），但它所依赖的那个格子是**单次抽样**抽出来的，第二次抽样就翻到了另一边。

**两个抽样给不出方差；三个也还不给。** 两个抽样只给一个差值，给不出这个差值的离散程度，所以 5.2.7 里那个数是**下界** —— 它可能低估种子变异，不可能高估。第三个抽样（5.2.8）把差值换成了一个**范围**，这比差值多、比方差少：3 draws give a range, not a variance estimate: a range is the distance between the extreme order statistics of the draws that exist, so it can only grow as draws are added and remains a lower bound on the spread the configuration actually has. It is more than a difference and less than a variance, and 3 draws are still few。两个抽样自己写明的读法不变：two draws give one difference and no interval on the spread, so this is a lower bound on seed variation: it can understate it and cannot overstate it. A real noise floor needs several seeds, which were not run.

#### 5.2.8 第三个种子：从差值到一个范围

5.2.7 的收尾自己说了它给不出什么：两个抽样只给一个差值，给不出离散程度，所以那个数是下界。
队列 43 用**同一套配置**又跑了一个抽样（GRPO G=4、lr 1e-5、150 步，只改 `seed`（3409））。
三个抽样仍然不是方差估计，但它能显示差值结构上看不见的一件事：第三个抽样落在那一对**里面**
还是**外面**。

**和前两次一样，它不作为本文件表格里的一列。** 它测的是同一个格子，列进去等于把一个配置

## 6. 评测与指标解释

### 6.1 Base 与随机不可区分

| 基线 | accuracy | macro-F1 | 来源 |
| --- | --- | --- | --- |
| 多数类 | 0.1190 | 0.0236 | `trivial_baselines.json` |
| 均匀随机（5 seed） | 0.1230 ± 0.0144 | 0.1211 | 同上 |
| **Base** | 0.2143 | 0.1347，95% CI **[0.0955, 0.1706]** | `comparison.json` |

Base 的 macro-F1 置信区间**覆盖**随机基线 0.1211，即零样本 Base 在 macro-F1 上与
随机猜测不可区分。引用 Base 的 macro-F1 时必须一并给出这一点。

### 6.2 两个结构化字段低于「恒答基线」——看似提升，实为未学会

初版评测只给分类与检索算了平凡基线，漏掉了结构化字段，而漏掉的正是最关键的对照。
补算后（`outputs/reports/structured_baselines.json`）：

| 字段 | 恒答基线（完全不看图） | Base | SFT | GRPO | 结论 |
| --- | --- | --- | --- | --- | --- |
| `defect_type` | 0.1190 | 0.2103 | **0.5840** | **0.6032** | 显著超过基线 |
| `radial_zone` | **0.8333** | 0.0794 | 0.2640 | 0.2698 | **全部未超过** |
| `clock_sector`（MAE↓） | 2.6932 | 5.0000 | **1.6847** | **1.7121** | SFT/GRPO 超过，Base 未超过 |
| `size_r`（MAE↓） | **0.1101** | 1.2139 | 0.4999 | 0.5695 | **全部未超过** |

含义必须说清楚：

- `radial_zone` 有 83% 的样本是 `center`，所以**永远回答 `center` 就能得 0.8333**。
  SFT 的 0.2640 和 Base 的 0.0794 都远低于这个下限。
  **但这一点需要重大修正，见 6.7**：这个 0.8333 的下限来自一个退化的标签，
  它衡量的是缺陷「质心」落在哪一带，而不是缺陷落在哪一带。对称图案（边缘环、
  随机分布、满片）的质心必然在圆心，于是标签被算术地压成 `center`。
  因此不能说模型「还不如不看图」——它回答的是另一个、更合理的问题。
  修正标签后模型的表现是**接近随机**（0.4560 vs 下限 0.5079），而不是远低于下限。
- `size_r` 则是一项**经得起推敲的真实失败**：模型预测与真值的相关系数仅 **0.0382**，
  即基本不含该字段的信息。它给出了 88 个不同取值（不是恒答），中位数 1.964 接近
  真值中位数 2.031，但散布与真值无关，于是 MAE 0.4999 反而大于恒答中位数的 0.1101。
  **这不是标签问题，是这个字段没有被学会。**
- `clock_sector` 是唯一一个微调后超过恒答基线的几何字段（1.6847 < 2.6932）。
  **但这一行有两个问题，见 6.8**：该 MAE 只覆盖 203/250 个样本，被排除的正是
  最难评分的那两类；而 Base 那一格的 5.0000 **只在 1 个样本上算出**（其余 251 行
  全部因解析失败被跳过），因此「Base 甚至差于均匀随机 3.0」不成立，该格应视为未测。
- 因此**不能声称模型学会了完整的结构化输出**：它学会了 `defect_type`，
  时钟方向有部分信号（但需按 6.8 打折），径向分区与尺寸没有学会。

这说明规格要求「随机/majority 基线」是必要的：没有基线，这两行会被当成改进写进结论。
本项目的基线现已覆盖分类、检索与结构化字段。**同时它也说明只有基线还不够：
基线本身必须建立在一个测量了它声称要测量的东西的标签上（6.7）。**

### 6.3 检索是下限而非调优结果

- 检索随机地板：mAP@10 0.0330 / nDCG@10 0.0596 / Recall@10 0.0394。
- 检索向量取自**固定 probe 的 mean-pooled 末层隐状态**，未经任何检索专项训练。
  因此所得指标应读作**下限**，不代表该模型在检索上的能力上限。
- GRPO 的检索同样是先把 adapter 合并为 bf16 再用同一 probe 打分
  （`models/Qwen3.5-9B-grpo-v1-merged`），与 Base/SFT 走完全相同的路径，
  否则三列不可比。合并后目录结构与已通过等价性校验的 SFT 合并模型一致。

### 6.4 训练/服务提示词不一致（基准低估 SFT）

- 基准的分类提示词与 SFT 训练时的提示词不同：基准无 system message 且措辞不同。
- SFT 在冻结基准上 accuracy 0.6230 / macro-F1 0.6114；
  在**训练格式**提示词上 accuracy **0.8849** / macro-F1 **0.8882**（95% CI [0.8492, 0.9223]）。
- 即基准数字**低估**了 SFT 的实际能力，差距来自提示词不一致而非模型能力。
- 该不一致**有意未在运行中途修改**，因为修改会使 Base 与 SFT 不再可比。
  上表训练格式数字是**诊断**，不作为榜单成绩引用。

### 6.5 约 2 个样本的评测差异

SFT accuracy 在完整基准上为 0.6230，在辅助分类集上为 0.63095，相差 2 个样本，
归因于批次组成与 padding 差异。与 6.6 是同一类数值噪声。

### 6.6 融合等价性：精确一致率 != 1.0 不代表失败

| 比较 | 行数 | 精确一致 | 功能一致 | 来源 |
| --- | --- | --- | --- | --- |
| **同一 adapter** 4bit vs bf16（噪声地板） | 60 | 0.4333 | 0.7000 | `outputs/merge_check/precision_floor.json` |
| adapter vs merged | 60 | 0.4667 | **0.7667** | `outputs/merge_check/equivalence.json` |
| merged vs merged（重跑，确定性） | — | 1.000 | 1.000 | 同上 |

答案是自由文本（caption/JSON），一个 token 的舍入差异会级联影响后续生成，
因此**精确字符串一致率衡量的是数值可复现性，不是正确性**。
关键结论：**merged 与 adapter 的偏离（0.7667）小于同一 adapter 单独改变精度的偏离（0.7000）**，
故融合是忠实的。不可把 `exact < 1` 读作"融合失败"。
比较仅在 60 行子集上进行，未覆盖全部 1512 行。

### 6.7 `radial_zone` 标签退化：它测的是「质心」而不是「位置」

这是本轮复核中**最重要的一项更正**，它推翻了 6.2 初版对 `radial_zone` 的判断。

`utils.py:139` 的规则是：

```python
def _zone(radius_ratio):
    if radius_ratio < 0.35: return "center"
    if radius_ratio < 0.72: return "middle"
    return "edge"
```

而特征里写的是 `"radial_zone": _zone(centroid_r)` —— **缺陷像素质心的半径**。
对任何关于圆心对称的图案，质心就在圆心，于是标签被算术地压成 `center`，
与缺陷实际在哪一带无关。实测（`benchmarks/wafer_bench_v1/structured.jsonl`）：

| 真实缺陷类型 | 中位质心半径 | 推出的标签 |
| --- | --- | --- |
| `Edge_Ring`（边缘环） | **0.063** | center |
| `Near_full`（满片） | 0.050 | center |
| `Random`（随机散布） | 0.044 | center |
| `Donut`（环） | 0.157 | center |
| `Edge_Loc`（边缘局部） | 0.333 | center（恰好卡在 0.35 阈值下） |

一个**贴在晶圆边缘的环**，质心半径只有 0.063，标签因此是 `center`。
全基准 **83.7%** 落在 `center` 桶里，全部是这一个机制造成的。

用 `outputs/reports/radial_zone_audit.json`（已先在 manifest 上验证与金标逐位一致，
251/251 精确相符、最大偏差 0）重新评分：

| 判据 | 金标分布 | 下限 | Base | SFT | GRPO |
| --- | --- | --- | --- | --- | --- |
| `centroid`（现状，质心） | center 210 / middle 36 / edge 5 | 0.8333 | 0.0794 | 0.2640 | 0.2698 |
| `mean_radius`（缺陷像素平均半径） | edge 123 / middle 128 | 0.5079 | 0.1310 | **0.4560** | 0.4444 |
| `outer_extent`（外沿半径） | edge 251 | 0.9960 | 0.1706 | 0.4200 | 0.4206 |
| `curate_rule`（本项目自己的验收规则） | — | 0.8333 | 0.1032 | 0.3240 | 0.3333 |

两点结论：

1. **换用「缺陷落在哪一带」的标签后，SFT 从 0.2640 升到 0.4560，下限同时从
   0.8333 降到 0.5079。** 说明模型的回答与「缺陷的位置」远比与「质心的位置」吻合，
   `radial_zone` 上 0.2640 这个数字**主要反映标签的毛病，而不是模型的毛病**。
2. **但换标签后模型仍然没有超过下限**（0.4560 < 0.5079），而且 `mean_radius`
   只有两个取值、随机水平就是 0.5。所以正确说法是：
   **模型在这个字段上接近随机，既不是「学会了」，也不是初版说的「远差于不看图」。**

另有一处词汇不一致：`prompts.py:56` 要求模型在
`center|middle|edge|full|none` 五值中作答，而 `_zone()` **永远不会返回 `full`**，
金标里 `full` 出现 0 次。SFT 有 **69/250**、Base 有 **189/252** 次回答 `full`，
这些**在构造上不可能得分**——模型使用了提示词明确提供的取值而被判错。

### 6.8 时钟 MAE 存在幸存者偏差，且被排除的正是最难的一类

`evaluate.py` 的 `clock_error` 用 `int(predicted)` 取值，失败即返回 `None`，
`structured_metrics` 随后**跳过该行**。所以公布的 MAE 是在「能解析的行」上算的。
被丢弃的答案实测为 `"all"` 与 `"none"` —— 模型在说「这个缺陷绕满一圈」或
「没有方向可言」。这是对提问的合理回答，却无法与单扇区金标打分。
来源：`outputs/reports/clock_parse_audit.json`。

SFT 丢弃 **47/250 = 18.8%**，且丢弃**不是随机的**：

| 类别 | 丢弃率 | |
| --- | --- | --- |
| `Random`（随机散布，无方向） | **24/30 = 0.80** | 过度集中 |
| `Edge_Ring`（闭合环，绕满 360°） | **18/30 = 0.60** | 过度集中 |
| 其余七类 | 0.00 – 0.12 | |

也就是说：**被排除的恰好是「单一钟点方向本就没有意义」的两类**，
保留下来的 203 行集中在方向确实良定义的类别上。因此 1.6847 这个数字
**是条件于一个比基准更容易的子集**，真实值应更差。GRPO 丢弃更多（54/252 = 21.4%）。

Base 更极端：**丢弃 251/252 = 99.6%，仅剩 1 行计分**。初稿写「九个类别的丢弃率
全是 1.00」，这句既**不成立**也**自相矛盾**：九个里八个确为 1.00（`Center`/`Donut`/
`Edge_Loc`/`Edge_Ring`/`Loc`/`Random`/`Scratch` 各 30/30，`none` 26/26），
**只有 `Near_full` 是 15/16 = 0.9375**；而若九个全是 1.00，就不该剩下任何一行。
支撑数取自冻结基准 `benchmarks/wafer_bench_v1/classification.jsonl` 的自身标签，
丢弃数取自 `clock_parse_audit.json` 的 `dropped_defect_types`（复核脚本
`tools/verify_droprate.py`）。由这两个事实可直接推出：**Base 唯一计分的那一行，
正是 `Near_full` 的幸存者** ——
Base 几乎一律回答 `all`/`none`。所以 Base 的时钟 MAE 5.0000 实际上是**在单个样本上**
算出来的，它「差于均匀随机 3.0」这一说法不成立，**不应作为任何对比的依据**。

**更正方向**（本次未实施，记录以免误读）：应当把「无方向」作为合法答案处理，
例如对 `Edge_Ring`/`Random`/`Near_full` 允许 `all`/`none` 并计入正确，
或将该字段改为方向性度量（`resultant_length`）而不是单扇区。

9. **数字完全正确，但被用反了方向 —— 溯源核对结构上看不见这一类。**
   5.2.2 初稿有一句：「同一个 5e-5 在 G=8 上把 KL 抬到 1.02–1.12」。
   1.1201 与 1.0217 两个数字都真实存在于记录中，逐字节核对通过；
   但 1.1201 属于 **lr1e-5** 那次，1.0217 属于 **lr5e-5** 那次 ——
   这个区间横跨了两个学习率，恰好把「学习率升高时 KL 是**下降**的」掩盖了。
   五份记录逐行重算（150 步 × 5 run）确认 `mean_kl` 与日志逐值相等，
   错误不在测量，在这句话。

   更麻烦的是：把方向反过来写**也是错的**。`kl` 是逐 token 均值
   （证据：在 `frac_reward_zero_std == 1` 的步上优势恒为 0，于是
   `loss == beta * kl` 严格成立 —— 十个 run 的全部 453 个空转步均满足（逐 run 实测为
54+49+23+57+63+40+50+11+57+49；初稿写 271，是一个加错了的旧数。逐 run 计数见
`kl_length_confound.json` 的 `runs.<tag>.kl_identity.idle_steps_tested` ——
不是 run 顶层的 `idle_steps_tested`，按后者查会什么都查不到，看起来像记录里没有这个数），
   最大偏差 2e-05，即日志自身的舍入）。但 5e-5 那四次的补全明显更短
   （GRPO(G=4) 115.48 → 97.92 token，−15.2%；GSPO(G=8) 114.40 → 109.16，−4.6%；GSPO(G=32) 118.10 → 113.74，−3.7%；GSPO(G=4) 116.97 → 113.83，−2.7%），
   均值取在不同的 token 跨度上，三次的 `kl` 不是同一个量。
   **因此该句被删除，而不是改写成相反方向。**

   同一段里的空转步论据犯的是第二种毛病：「把空转步从 36.00% 推到 38.00%」
   拿 GRPO(G=4, lr1e-5) 比 GSPO(G=8, lr5e-5) —— 算法与组大小同时变了。
   四个**同算法同组大小**的对照方向并不一致：
   GRPO(G=4) 36.00% → 32.67%（`idle_delta` −0.0333）、
   GSPO(G=8) 15.33% → 38.00%（`idle_delta` +0.2267）、
   GSPO(G=32) 7.33% → 42.00%（`idle_delta` +0.3467）、
   GSPO(G=4) 33.33% → 26.67%（`idle_delta` −0.0667）。
   即「学习率把空转步推高」只在 GSPO(G=8)、GSPO(G=32) 上成立，GRPO(G=4)、GSPO(G=4) 都把它压低。

   **这一类的教训与前面八条不同：**前八条防的是「数字来路不明」，
   这一条防的是「数字来路清楚、但话说的不是它」。
   前者可以自动核对，后者目前**只能靠重算该比较本身、并检查符号** ——
   `tools/kl_length_confound.py` 就是为此写的，它把两个方向的证据
   （恒等式、补全长度）与结论一起存档，任何人可复跑。
   全部数值见 `outputs/reports/kl_length_confound.json`。

   今天又添了一组同类实例，而且是**一次 run 落地同时触发四处**（GSPO(G=4) lr5e-5）：
   (1) 5.2.5 里「时钟 MAE 最低的是 SFT」与「尺寸 MAE 最低的是 SFT」两句同时失效 ——

    退出码是 0，于是在日志里记下 `ok`。**不到一分钟之后**，队列 43 —— 它一直在等的
    正是这两个补丁 —— 启动了那个文件，第三次抽样的训练在第一行就死了。

    更值得记的是第二层：同目录的 `tools/patch118_grpo_train_fixes.py` **会** 在
    `bash -n` 失败时还原文件，而它上一步就主动让位了，理由是 patch75 已经写进了它要找的
    那个字段。也就是说，唯一能拦住这件事的那个检查，**按构造就不可能被执行到**。

    代价不是猜测：训练进程当场退出，而队列脚本的下一步是等 `train_result.json`，
    上限三个小时。如果没有人在旁边看，这张卡会从那一刻起空转到超时，第三次抽样一次也
    不会跑 —— 而「等到超时」和「正在训练」在日志里长得一样。实际发现得早，空了约五分钟。

    第二处，`tools/check_quantified_claims.py` 的第 11 项检查 —— 那张「记录写的与自己
    日志不符」的表 —— 由 `patch118` 在**同一次运行里**写下，同一次运行也重新生成了它要读
    的那张表。它的模式要求表头出现在行首；而那张表在文档里挂在编号条目下面，每一行都
    缩进四个空格。于是它一次也没有匹配过：锚点失配、打印 STALE、退出 1 —— 而 patch118
    自己的日志里就印着那一行，紧接着调用者记下 `ok`。从那一天起，第 11 条那张表没有任何
    东西读过；**而第 11 条讲的正是一个没有任何东西去核对的「记录」。** 今天把四个空格
    补进模式之后它第一次真的跑起来，四条比对全部通过：表本身是对的，从来没有跑过的是
    读它的那个检查。

    第三处方向相反：`tools/audit_report_numbers.py` 把文档引用的**证据**当成了文档的缺陷。
    `LIMITATIONS.md` 逐字引用了包装脚本那一行（`RUN_TAG="${RUN_TAG:?…}"`），因为那行正是
    一次训练丢失的原因，值得原样留下；而「未填模板字段」这条规则把它读成了一个没人填的
    模板字段，拒绝继续，把 42 号 run 的落地停在那里。**这条规则从没跑过一次「文档引用一行
    shell」的输入。** 修法是在两处收窄：`${...}` 是展开而不是模板字段，且格式说明符从不以
    `?` 开头。收窄用两个方向量过：真正没填的字段 —— 包括写在代码片段里的 —— 仍然会让这个
    环节停下来，而引用那行 shell 不再会。这是三处里唯一一处「检查按设计工作了、而设计本身
    是错的」，它和另外两处是同一个病：没有人拿它要读的输入试过它。

    第四处不是检查，和前三处同一天出现，出现在写这一条的过程中。`tools/post_consolidation.sh`
    里的 `WATCH` 列表写明「评估最后发生的那些 run」以及每个 run 的评估被告知的合并目录 ——
    它是三个条目，第三次抽样不在其中：那份名单写在它被启动之前。它漏掉的后果很窄，却完全
    安静：如果第三次抽样的评估没有把检索字段写进报告，这个环节既不修也不报，**它照样印出
    自己的完成标记**。唯一会响的是 `land_run.sh` 在那里等那个字段，上限六个小时然后停下 ——
    从外面看，这和一个还在训练的 run 一模一样。补进去时，条目里的两个字符串是从该 run 自己
    的队列脚本里抄的，不是重新写的，改完照例过了一遍 `bash -n`。

    这是今天第二份因为「写下来时是对的」而短了一行的清单（第一份是 44 号脚本的 `REQUIRED`，
    见第 16 条第四条），也是唯一一处**在被记录的那条缺陷里、边写边撞见的新实例**：
    发现它不是在找它，而是在为别的原因读那份脚本。所以它留在这里，而不是被当成题外话删掉。

    四处合起来是今天最该记的一句：**一个拦不住被检查对象的检查，就是一行日志。**
    这两种形状本文档都分别记过（第 15 条的「机制存在但从未运行，而它自己的自检通过」、
    第 16 条第一条的「失败被调用者印成 WARNING」）。记下来并没有挡住下一次 —— 因为
    共同点不是形状，而是**每一个检查的失败路径看起来都正常**：失败信息印出来了、
    STALE 印出来了、告警印出来了，而没有任何一步的退出码因此改变。
    所以这三处都不是靠读代码发现的，是靠**让它们跑一次**发现的：patch75 的检查直到
    被拿它自己的输出试过才拦人，第 11 项直到把表交给它才第一次比对，未填字段那条直到
    有人拿一份真文档问它才现形。

19. **一次真实的盘满，和它伪装成的三样东西 —— 外加一条从未跑过一次的修复路径。**
    第三次抽样的评估走到合并那一步时盘满了。报错是 `SafetensorError: ... No space left
    on device (os error 28)`，18:43 写进队列日志 —— 存盘挂在 200 G 的 `/autodl-fs/data`
    上，当时空闲 52 M。这一条记的不是「盘满了」，而是**盘满之后，这套流程把它显示成了
    另外三样东西，而三样都没能把人叫醒**，以及它顺带暴露出的第四件、与盘无关的事。

    第一样，一个**看起来完整的产物**。合并死在写权重的中途，留下一个 4.6 G 的
    `...-seed3409-merged` 目录：`.safetensors` 已经写出来了，缺的是
    `preprocessor_config.json` 和其余配置。而判「要不要重新合并」的那句测试问的恰好是
    **「有没有 `.safetensors`」**。于是这个半成品不但会被当成成品留在那里，还会让下一次
    尝试**跳过合并、直接拿去排序**，并且一直这样做下去。这正是第 14 条那一类：一个与
    完整产物无法区分的产物。与之前记过的几次的区别在于，那几次是「产物在、内容是旧的」，
    这一次是**产物在、却根本不能用**，而唯一能暴露它的线索（少一个配置文件）比要读它的
    那个测试更不起眼。

    第二样，**一次被印成 WARNING 的死因**。排序接手这个目录后报
    `OSError: Can't load image processor`，调用它的那一行把它印成
    `WARNING: GRPO retrieval failed`，然后继续往下走。这是第 16 条第一条的形状；在这里
    代价更具体：那行 WARNING 之后没有任何东西停下。

    第三样，**一个读起来像「没测过」的空单元格**。报告里的 `retrieval` 保持 `null`，
    表格把这个 `null` 渲染成「未运行」—— 也就是「这一项没有做」。真实情况是这一项
    **做了，而且死在半路**。第 14 条记的是「产物与完整产物无法区分」，这里是它的镜像：
    **失败与未尝试无法区分**，而两者的后续处理完全一样 —— 什么都不做。最后 `land_run.sh`
    进入它等这个字段的六个小时上限；**等待超时和正在训练，从外面看一模一样**，这是今天
    第三次撞上这句话（前两次见第 18 条）。

    第四件与盘无关，而且比上面三样都早：**那条唯一能修好检索字段的路径，从未成功运行过
    一次**。`tools/watch_retrieval.sh` 是 `post_consolidation.sh` 用来补 `retrieval` 的
    兜底，做三件事：合并、排序、重新打分。它的合并一步把**检查点根目录**交给了
    `swift export` 的适配器参数，而训练把适配器写在根目录下面一层：
    `<root>/v0-<日期>/checkpoint-150/adapter_config.json`。得到的回答是
    `AssertionError: ... is not an adapter`。也就是说，**这个脚本的合并阶段对本项目的
    任何一个 run 都不成立** —— 早先那些 run 的目录结构完全一样。今天唯一一个检索被真正
    测出来的 run，是被 `30_eval_grpo.sh` 自己的第 3b 步测的，那一步用 `find` 解析适配器，
    所以从来没有碰上这件事。一个**存在、被依赖、却一次也没有跑通**的兜底：第 15 条的
    形状；区别在于它没有自检可以「通过」，它只会在被需要的那一晚印一行失败，然后重试。

    修法和腾空间的做法：适配器的解析改成与 `30_eval_grpo.sh` 同一段 `find`（取目录
    本身、按版本序取最新检查点），并在没有适配器时直接给出「未测量」这个有字的结果，
    而不是拿空参数每分钟调一次 `swift export` 试半小时；腾空间是删掉那个 4.6 G 的半成品
    和三个已经留了排序结果的合并目录，一共约 29 G，**检查点（每个约 19 G，是训练的原始
    记录）和基座模型没有动**。这一条最后要留下的是那句判断：这套流程里「已经有一份产物
    了」的判断不止一处，而它们问的都是**文件在不在**，不是**它能不能用**。

20. **两个终点标记：一个把两个分支写反的守卫，和一句声明自己记下了什么的话。**
    这两处都在今天收尾的那条链上，也都被那条链自己在同一天晚上撞出来。它们比第 18 条
    记的那些更贴近要害一点：第 18 条记的是**检查**拦不住东西，这两处是**标记**在说谎 ——
    而收尾链从头到尾靠的就是标记。

    第一处，`44_final_consolidation.sh` 的等待名单守卫。它是今天下午 17:34 才写下的，
    针对的正是下午真的发生过的那件事：第三次抽样漏在等待名单外面。守卫的形状是

        if ! "$PY" - ... <<'GUARDPY'
        ...
        GUARDPY
        then
          echo "wait list check: covers the enumerated run set"
        else
          echo "FATAL: the wait list does not cover the enumerated run set (see above)"
          FAILED=1
        fi

    那个 `!` 和两条消息的分支是对调的：**检查通过的时候走 else、印 FATAL、并把 FAILED
    设上，而 FAILED 决定完成标记印不印。** 也就是说，从写下的那一刻到今晚，这个脚本
    **不可能**打印它的完成标记；而 `post_consolidation.sh` 的第一步等的正是那个标记。
    没人看见，因为这个守卫**是第一次执行** —— 17:34 写下，44 号下一次运行就是今晚 18:57。
    今晚它确实印出了两句互相矛盾的话：「wait list covers every run run_set.py accounts
    for (12)」和「FATAL: the wait list does not cover the enumerated run set」。两句都是
    真的，是关于不同东西的真话。

    值得注意的是发现方式：不是读代码，是**把两个方向各跑一次**。改前拿真实的守卫文本
    试，检查通过走向 FATAL；改后同样两个方向，通过走向 covers、失败走向 FATAL。
    同一条守卫在写下的那天如果被拿它自己的两种结果试过一次，它活不到今晚 ——
    这正是第 18 条那句「一个拦不住被检查对象的检查，就是一行日志」的又一处，只是这一次
    **检查本身是反的**，它不是在放行，它是在拦住正确的那个结果。

    第二处方向相反：`tools/post_consolidation.sh` 等不到标记时印的那句 WARNING 说它
    「继续，并记下这一趟是在没有确认前驱的情况下跑的」—— **而它什么也没记**。
    `predecessor` 这个词在整个文件里只出现一次，就在那句话里：没有标志、没有产物，结尾
    那行完成标记对前驱一个字也不说。也就是说，一个读者最需要知道的状态（这些文档是在
    没有确认前驱的情况下重建的）被宣布为「已记录」，然后没有被记录。

    修法是今天能给出的最弱、也是诚实的一种：一个标志，加上一个**带限定语的完成标记** ——
    有前驱时印 `post-consolidation pass complete`，没有时印
    `post-consolidation pass complete (WITHOUT a confirmed predecessor)` 并在下面写明
    为什么。这不是新增一个检查，是撤掉一句假话：那两行字现在说明的状态，和实际发生的
    状态是同一个。

    这两处在今晚之所以值得单独记一条，是因为它们都长在**收尾链自己的标记**上。一条链
    的每一环都用「上一环印了那句话」来确认自己不是在没有前驱的情况下开工，而这一环的
    守卫写反了、那一环的 WARNING 说了自己没做的事 —— 于是从 17:34 到 19:06，没有任何
    东西真正检查过这条链是否完整；它靠一句 WARNING 和一行 FATAL 的措辞来自证清白。
    收尾链重新跑过一遍之后，标记是干净的、等待名单守卫两个方向都验过，但这一条要记的
    不是「修好了」，而是**这条链的完整性一直是由它自己不印的那句话来保证的**。
